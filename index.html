#11212. How I Built a CRM with Vibe Coding Instead of Spending $1,000+ on App Builders

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

Stay up to date with AI tools, model releases, and developer workflows that matter.

I have designed more than 100 websites and helped clients set up over 12 CRM and ERP systems. For years, my work revolved around WordPress, digital marketing, business automation, and helping companies choose the right technology.

But building a web application from scratch was a different challenge.

I wanted to move beyond configuring existing software and experience the entire product development process myself. I had an idea, a clear understanding of business workflows, and access to AI coding agents. What I did not want was another expensive subscription that would limit how I built, deployed, or maintained the application.

That decision led me to build a CRM using Claude, Next.js, Firebase Firestore, Tailwind CSS, Vercel, and Git.

The experience taught me something important: AI can reduce the cost of building software, but understanding what you are building still matters.

My background gave me a useful starting point. After working on more than 100 websites, I understood how users interact with interfaces, how businesses collect leads, and why a confusing workflow can make even good software difficult to use.

Setting up CRM and ERP systems for clients also helped me understand the operational side of software. I had seen how businesses manage contacts, sales pipelines, follow-ups, and reporting.

However, configuring an existing platform and building an application from scratch are two very different experiences.

When you configure a CRM, many architectural decisions have already been made. When you build one, you must think about the data model, authentication, permissions, integrations, deployment, and what happens when something fails.

I decided to use this project to learn those things through practical experience rather than limiting myself to website design.

My first instinct could have been to use a visual app builder such as Lovable or Bolt. These tools can be excellent for quickly generating prototypes and getting an idea off the ground.

But I wanted greater control over the codebase, architecture, and deployment process. I also wanted to avoid accumulating app-builder subscription costs during development.

Instead, I chose an AI-assisted coding workflow.

Claude acted as my coding partner. I described requirements, generated implementation drafts, reviewed the output, debugged problems, and refined features through repeated iterations.

This did not mean I could simply write a prompt and receive a finished application. I still had to make decisions, understand the generated code, test the results, and correct mistakes.

The financial advantage was meaningful. By avoiding paid app-builder subscriptions for this project, I saved more than $1,000 in potential tool costs and related expenses I would otherwise have budgeted for. That was my project-specific saving, not a claim that every custom application will be cheaper to build.

More importantly, I ended up with a codebase and development workflow I could control rather than depending entirely on a particular app-building interface.

I wanted a modern stack that supported fast iteration without sacrificing control over the application.

Claude helped me translate requirements into code, work through implementation problems, and iterate on features. I treated its output as a starting point, not something to trust without review.

Next.js provided the foundation for the web application. It gave me a structured way to build the interface and application logic while keeping the project organized as it grew.

Firestore handled the application's data storage. Its document-based model and integration with the Firebase ecosystem made it a practical choice for my development workflow.

Choosing a database is only part of the job, though. Data structure, access rules, query patterns, and the way records relate to users all require careful thought.

Tailwind CSS helped me build and refine the interface without maintaining a large collection of separate CSS rules. It also made iterative UI improvements easier.

Git gave me a history of code changes and a way to manage development safely. When an AI-generated change caused a problem, version control helped me inspect what had changed and recover when necessary.

Vercel provided the deployment environment for the application. Its integration with Git made it easier to move from code changes to deployed versions.

Together, these tools allowed me to build with AI assistance while retaining control over the underlying code and deployment process.

The biggest surprise was how quickly AI could produce a first version of a feature—and how much work could remain afterward.

A screen might look correct but behave incorrectly when connected to real data. An API integration could work in a simple test but fail when an external service returned an unexpected response. A feature could appear complete while overlooking permissions or edge cases.

Connecting different services required more than generating a request. I had to consider authentication, request and response formats, error handling, timeouts, and what the application should do when an external service became unavailable.

I learned to break integrations into smaller steps and verify each one before building additional functionality around it.

An application that stores customer information cannot rely on a good-looking login screen for security.

I had to pay attention to authentication, database access rules, permission boundaries, and the possibility of users accessing data they should not see. AI assistance made implementation faster, but security decisions still required careful review and testing.

A feature can technically work and still feel frustrating to use.

I learned to pay attention to loading states, error messages, navigation, responsiveness, and how many steps users needed to complete common tasks. I also had to think about how database queries and application behavior would change as the amount of data increased.

These were not problems that could be solved by writing a better prompt alone. They required observation, testing, and repeated refinement.

The most valuable lesson was that vibe coding is not the same as handing over software development to an AI model.

The developer's role changes. Instead of writing every line manually, more time goes into defining requirements, directing implementation, reviewing code, testing behavior, and deciding which trade-offs are acceptable.

My experience in WordPress and business systems helped me understand the workflows I wanted to support. AI coding tools helped me move from those requirements to a working implementation more quickly.

The combination was more valuable than either one on its own.

I also learned to avoid building too many features at once. Small, testable changes made debugging easier and helped me understand the application as it evolved.

Finally, I realized that shipping an application is not the end of the work. Maintenance, security updates, monitoring, and improvements based on actual usage remain important after launch.

Building this application expanded my skills beyond website design and configuring third-party software. I gained hands-on experience with application architecture, database integration, API workflows, version control, and deployment.

The project also became a meaningful addition to my personal portfolio. You can read the NeerSoft CRM project case study to see how I approached the build.

I am not suggesting that every business should build its own CRM or that app builders are the wrong choice. For some projects, a ready-made platform is the fastest and most economical option. For others, a visual app builder is an excellent way to validate an idea before investing in custom development.

The right approach depends on the requirements, budget, technical constraints, and long-term plans.

For me, building from scratch with AI coding assistance was the right learning experience. It helped me avoid more than $1,000 in potential app-builder costs while giving me greater control over the application and teaching me skills I could not have gained by configuring an existing platform alone.

My biggest takeaway is simple: AI makes building software more accessible, but the ability to define problems, make sound technical decisions, and verify the results is what turns generated code into a useful application.

Meta description: Build a reliable analytics pipeline with SQL. Learn to handle duplicate records, late updates, data quality tests, and reporting before warehouse migration.

A dashboard can load quickly and still report the wrong number. A retried import might count an order twice. An update might arrive after the daily report has run. A join might multiply rows without producing a database error.

For developers moving application data into analytics, these problems deserve attention before platform selection. A larger warehouse can process an incorrect query faster, but it cannot decide what your metrics should mean.

This tutorial walks through a small order-reporting pipeline. You will define the grain of a dataset, handle repeated deliveries, select the latest record version, and test the output before exposing it to a dashboard.

“Show daily sales” sounds specific until someone asks which date, currency, or order status counts.

That final distinction matters. If an order changes from paid to refunded, this report removes it from the paid-order total on its original order date. It does not record a refund event on the refund date.

An accounting-style report would need a different model, usually based on transactions or adjustments. A table of current order states cannot answer every historical question.

A useful pipeline has three responsibilities:

●     Raw storage preserves incoming records and ingestion metadata.

●     Staging models normalize types, identify duplicates, and apply source ordering rules.

●     Reporting models express business definitions at a documented grain.

Keep these responsibilities distinct even if they initially live in one database.

For example, raw data might contain five deliveries of an order update. Staging resolves those deliveries to one current order. Reporting then groups qualifying orders into daily totals.

This separation gives failures a location. If the raw layer is missing an update, changing the dashboard query will not fix the extraction process.

Eight eMudhra intermediate Certificate Authority private keys are trivially recoverable from their public certificates. Any attacker can mint trusted TLS certificates for arbitrary domains. Browsers have already blocked these compromised intermediates through revocation mechanisms, but most non-browser runtimes — curl, Python, Node.js, Go, and Rust — still silently trust them. This affects any team operating server-side infrastructure, CI pipelines, or CLI tooling that makes outbound TLS connections. If your stack trusts the eMudhra chain, an attacker can forge certificates your code will accept without complaint.

This guide provides a diagnostic sequence: test every runtime in the stack against the compromised certificates, remediate by updating trust stores, and verify the fix sticks. The primary source for this disclosure is Scott Helme's detailed writeup.

In RSA key generation, you derive the private exponent d via the modular inverse of the public exponent e modulo λ(n) (the Carmichael totient of the modulus), where λ(n) depends on the prime factors of n. RSA's security depends entirely on d being large — typically hundreds of digits — making it computationally infeasible to derive from the public key alone.

eMudhra generated eight intermediate CA certificates with single-byte d values. Specific recovered values include d=4, d=56, and d=115, as documented in Scott Helme's disclosure post. These are not large numbers. They are recoverable from the public certificate in milliseconds. Anyone with access to the public certificate (which is, by definition, public) can reconstruct the private key and sign certificates that chain up to eMudhra's trusted root. That means arbitrary TLS certificates for any domain, indistinguishable from legitimate ones to any client that trusts the eMudhra chain.

An attacker holding one of these recovered keys can issue a certificate for any hostname, and any TLS client trusting the eMudhra intermediate will accept it without complaint.

The problem lies everywhere else. Non-browser TLS clients skip revocation checks by default. curl does not check CRLs or OCSP unless explicitly configured to do so. Python's requests and urllib3 libraries rely on the certifi bundle and perform no revocation checking. Python's standard library urllib.request module uses the system SSL store, not certifi. Node.js's https module uses either a compiled-in root store or the system store depending on build configuration, with no active revocation. Go's crypto/tls loads system roots but does not perform revocation checks. Rust's rustls paired with webpki-roots uses a bundled Mozilla root set, while native-tls defers to the system store; neither checks revocation by default.

This creates a trust store gap. The system CA bundle on a Linux server, the certifi bundle shipped with Python, and the compiled-in roots in Node.js might all still contain the eMudhra intermediates or trust the root that chains to them. Without manual intervention, these runtimes remain vulnerable.

Every frontend developer will eventually stare at a CORS error in the browser console, watching an API call fail for reasons that seem opaque. A CORS error fix requires understanding what the browser is actually telling you, matching that specific message to its root cause, and applying a targeted, security-conscious server configuration.

The scheme, host, and port together define an "origin." https://example.com and http://example.com are different origins (different schemes), as are https://example.com and https://api.example.com (different hosts). https://example.com and https://example.com:443 are the same origin because port 443 is the default for HTTPS, and browsers omit it in origin comparisons. The browser enforces the same-origin policy on client-side JavaScript reading responses, not on sending requests. This distinction trips up many developers: the server may still receive and fully process the request; the browser simply refuses to expose the response to the calling code. The request lands, the database row gets written, and the browser throws an error anyway. The policy exists to prevent a malicious page from silently reading sensitive data from another origin using the user's ambient credentials.

Cross-Origin Resource Sharing (CORS) is a controlled opt-in mechanism via HTTP response headers. The server signals to the browser that a specific foreign origin is permitted to read its responses. Four headers control the mechanism: Access-Control-Allow-Origin specifies which origin is allowed, and Access-Control-Allow-Methods declares which HTTP methods are permitted. Access-Control-Allow-Headers lists which custom or non-simple headers the client may send, while Access-Control-Allow-Credentials indicates whether the browser should expose the response to credentialed requests.

The browser does not treat all cross-origin requests equally. "Simple" requests use GET, HEAD, or POST with a Content-Type of application/x-www-form-urlencoded, multipart/form-data, or text/plain, and no custom headers. A POST with Content-Type: application/json is not a simple request and triggers a preflight.

Simple requests go directly to the server, and the browser evaluates the CORS headers on the response. Anything else triggers a preflight request: an OPTIONS call the browser sends automatically before the actual request, asking the server whether the real request would be acceptable. If the OPTIONS response lacks the proper CORS headers, the browser never sends the real request at all.

A typical Chrome DevTools error reads: Access to fetch at 'https://api.example.com/data' from origin 'https://app.example.com' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

Two origins appear in this message. The URL after "fetch at" is the target server, the resource the code tried to reach. The value after "from origin" is the page's own origin, the one making the request. Chrome is stating that the target server's response did not include an Access-Control-Allow-Origin header that matches the requesting origin, so the browser blocked the response from reaching JavaScript.

The most common variant is the missing header: No 'Access-Control-Allow-Origin' header is present on the requested resource. The server simply did not include the header at all.

When the console says Response to preflight request doesn't pass access control check, the server either did not respond to the OPTIONS request correctly or returned a non-2xx status code for it.

Redirect variant: Redirect is not allowed for a preflight request. Developers commonly misdiagnose this one. It occurs when the URL triggers a redirect before reaching the application handler. Typical culprits include HTTP-to-HTTPS upgrades, trailing-slash normalization (e.g., /api/data redirecting to /api/data/), or a load balancer rewriting URLs. The browser's preflight OPTIONS request follows the redirect, and the Fetch specification (§4.8) forbids following redirects on preflight requests, so the entire flow fails. Fix the URL so no redirect occurs.

Credential variant: The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '*' when the request's credentials mode is 'include'. When fetch is called with credentials: 'include' or XMLHttpRequest sets withCredentials = true, the server must respond with the exact requesting origin, not *. The browser will block JavaScript access to the response if a wildcard is used with credentials.

Before modifying any server code, verify what the server actually returns by simulating a preflight request from the command line:

The -i flag prints response headers. -X OPTIONS sets the HTTP method to OPTIONS, mimicking the browser's preflight. The Origin header declares the requesting origin. Access-Control-Request-Method tells the server which method the real request would use. Access-Control-Request-Headers lists the custom headers the real request would include.

If these are absent, the server is not configured for CORS. If the response is a 301 or 302 redirect, the redirect variant is the culprit.

During local development, the least-configuration way to eliminate cross-origin issues is to proxy API requests through the dev server so the browser sees all traffic as same-origin.

With this configuration, a fetch('/api/users') call from the frontend at http://localhost:5173 is forwarded to http://localhost:3001/users. The browser never sees a cross-origin request. When Nginx sits in front of a backend, it is often the right place to manage CORS centrally. Important: Do not use if with add_header inside a location block -- Nginx's if block causes all parent-scope add_header directives to be silently ignored, breaking CORS headers on actual (non-OPTIONS) API responses.

The map directive builds an allowlist: if $http_origin matches a listed value, $cors_origin is set to that value; otherwise it remains empty. The always parameter ensures headers are added even on error responses (4xx, 5xx), which is critical because Nginx's add_header without always silently drops headers on non-2xx responses.

Nginx's if directive creates a new configuration context. Any add_header inside an if block discards all add_header directives from the enclosing scope.

Why the if block contains all headers and return 204: By placing return 204 inside the if block, the OPTIONS request is fully handled there and never reaches the outer add_header directives or proxy_pass. Non-OPTIONS requests skip the if block entirely and the outer scope's add_header directives and proxy_pass handle them. This separation avoids the inheritance pitfall: each request path (OPTIONS vs. non-OPTIONS) has its own complete, self-contained set of headers.

Note on empty $cors_origin: When the allowlist excludes the origin, $cors_origin resolves to an empty string, and Nginx emits Access-Control-Allow-Origin: (a blank header). Browsers will reject CORS for the request, which is the correct security outcome. However, emitting a blank header is technically non-conformant with RFC 6454. The most robust production solution is to handle CORS in the application layer (Express/Next.js) and have Nginx proxy transparently, or to use OpenResty/Lua for conditional header suppression.

After deploying, verify that both curl -X OPTIONS and curl -X GET against the same URL return the expected CORS headers.

A frequent source of the redirect CORS variant is a proxy_pass trailing-slash mismatch. If the location block is location /api but proxy_pass is http://127.0.0.1:3001 (no trailing slash), Nginx may issue a redirect for /api/ normalization before the request reaches the handler. Similarly, a return 301 https://... rule placed before the CORS location block can redirect the OPTIONS preflight. The fix is straightforward: ensure trailing slashes match between location and proxy_pass, and place any redirect rules after or outside the API location block so they do not intercept OPTIONS requests.

Use an explicit origin allowlist. Avoid * when credentials are involved; the browser will block JavaScript access to the response if a wildcard is used with credentials: 'include'.

Restrict Access-Control-Allow-Methods to only the methods the API actually uses. Listing every HTTP method widens the attack surface unnecessarily.

Set Access-Control-Max-Age to cache preflight responses. Chrome caps this value at 7200 seconds (2 hours); Firefox honors up to 86400 (24 hours). Use 7200 as a safe cross-browser default, or 86400 if your users are primarily on Firefox and you want fewer preflight round-trips.

Include Vary: Origin on every response where Access-Control-Allow-Origin is set conditionally. Without it, CDN or proxy caches may serve a CORS response cached for one origin to a different origin, causing intermittent failures.

Never mirror the request Origin header back without validating it against an allowlist. This is an open CORS misconfiguration that effectively disables the same-origin policy for any attacker-controlled origin.

Do not install browser extensions that disable CORS either -- they mask the problem during development and expose you to real cross-origin attacks on every other site you visit.

Avoid adding CORS headers in both the application framework and Nginx simultaneously. Duplicate Access-Control-Allow-Origin headers cause the browser's CORS origin comparison to fail; the browser receives the response but blocks JavaScript from reading it, producing the same CORS error the fix was meant to resolve.
