Penguin Solutions showed off its MemoryAI Photonic Appliance remote memory system at Supercomputer 2026 (SC26), with customer samples scheduled for the second half of 2027. The device supports up to 576 GB of HBM3E with an aggregate bandwidth of up to 7.2 TB/s, and connects to systems using optical interconnects via the CXL.mem 3.1 protocol. HBM memory capacity is usually one of the major bottlenecks of contemporary AI accelerators, which is why, when developers face it, they tend to add or upgrade their accelerators. Penguin Solutions' new device aims to solve that, but there are drawbacks.

The MemoryAI Photonic Appliance is designed to accommodate up to 576 GB of HBM3E and 16 TB of DDR5 memory, with overall bandwidth targeting 7.2 TB/s. The external memory box supports three memory access configurations: HBM Direct Mode, HBM-DDR5 Cached Mode, and DDR5 Direct Mode. The first provides access to external HBM3E, the second combines HBM3E and DDR5 in a tiered memory sub-system with HBM3E acting like a write-through cache for DDR5, while the third provides access to DDR5 without an intermediate HBM cache. Meanwhile, hardware semaphores (HSEMs) enable software-managed memory consistency across multiple host processors (i.e., if more than one host processor accesses the same memory location, software can use semaphores to ensure that only one host processor can modify data).

The Penguin appliance relies on Marvell's architecture that consists of Photonic Fabric Memory Modules (PFMMs) and Photonic Fabric network interface cards (PF-NICs). The device uses eight PFMM modules; each integrates a memory controller, eight DDR5 DIMM interfaces, 72 GB of HBM3E cache, and a photonic interposer with 16 transmit and 16 receive channels operating at 224 Gbps. This provides approximately 7.2 Tbps of aggregate bidirectional optical bandwidth per module, or 57.6 Tbps (7.2 TB/s) for the entire appliance, equivalent to approximately 3.6 TB/s in each direction.

Marvell offers two ways to connect processors to the external memory pool. The first uses a Photonic Fabric network interface card (PF-NIC) with PCIe 6.0 and CXL 3.1 connectivity, which provides up to 2 Tbps of bandwidth and memory access latency below 350ns, excluding PCIe/CXL overhead. The second relies on a Photonic Fabric chiplet integrated into an XPU, which offers up to 14.4 Tbps of bandwidth and latency below 200ns. Both approaches enable processors to access shared memory over optical links across distances of up to 30 meters. Meanwhile, the chiplet approach requires accelerator designers to install the chiplet, while transparent memory expansion using the PF-NIC requires the host to support its memory mapping at both the hardware and software levels.

Marvell's architecture is designed to enable compatible host systems to access external memory through ordinary load/store memory operations rather than RDMA data transfers, but this requires specific hardware capabilities on the host side. Most modern CPUs support PCIe as well as the CXL.mem protocol for memory expansion. However, the situation is different for AI GPUs.

Nvidia's data center GPUs support PCIe, NVLink, and various memory management mechanisms, but they do not support a general-purpose CXL.mem host interface for memory expansion. Similarly, AMD's Instinct accelerators use PCIe and Infinity Fabric for connectivity, but they do not generally support CXL.mem. In theory, accelerators without native CXL.mem support could theoretically access the appliance through a CXL-capable CPU, provided their coherent interconnect supports access to CXL-attached memory. However, this would introduce additional latency, which will extend well beyond the advertised sub-350ns figure (which already excludes PCIe/CXL overhead), which could greatly reduce the actual performance benefits provided by extra capacity.

As a result, PFMMs and Penguin's MemoryAI Photonic Appliance can extend usable memory capacity only for select host systems without major performance penalties. These could include custom XPUs equipped with Marvell's Photonic Fabric chiplets, CPUs or other PUs that support CXL.mem and PF-NIC with memory mapping mechanism, and potentially future AI accelerators that support CXL.mem or integrate Marvell's Photonic Fabric. Obviously, this means that such systems will get an indisputable advantage over machines based on conventional accelerators from AMD and Nvidia in the form of memory upgrades.

Speaking of advantages, we must note that while an aggregate bi-directional bandwidth target of 7.2 TB/s (3.6 TB/s in both directions) seems formidable (it is only a bit lower than memory bandwidth of B300 SXM that comes at 7.7 TB/s), it is set to be shared between multiple accelerators (eight accelerators in a hypothetical scenario), which will provide limited bandwidth to each one. Although Penguin promises transparent access to external memory without modifications to applications, the appliance will require compatible memory management software (in addition to host hardware), which will treat external memory as another memory tier. While extra memory is always welcome, performance benefits of complex multi-tier memory subsystems depend heavily on workloads and efficient data placement. Consequently, the appliance's practical advantages remain to be demonstrated.

Penguin showcased the appliance this week; however, customer samples are scheduled for the second half of 2027, which likely means that the device and/or underlying hardware, firmware, and software need polishing. That said, practical performance and economic advantages of Penguin's MemoryAI Photonic Appliance remain to be seen when everything works as intended. In any case, do not expect deployments of such systems before 2028. This begs the question of where Penguin Solutions plans to source HBM3E in volume in 2028, when the industry will have transitioned to HBM4 and will be in the midst of transition to HBM4E.

#10245. November Patch Tuesday: An Overflowing Cornucopia of CVEs

Microsoft serves up an actively exploited Outlook zero-day, and a wave of critical Exchange, SharePoint, Windows Search, and LDAP bugs that exhausted defenders need to prioritize fast.

November offers up a veritable Patch Tuesday feast of vulnerabilities that are more likely to be exploited. In its second four-digit Patch Tuesday release in a row, Microsoft today addressed 1,093 security vulnerabilities, with 63 rated critical, and one zero-day in the mix (CVE-2026-124194, CVSS 6.5) that Microsoft confirmed is under active exploit.

"Most security teams haven't quite recovered from the last month of bumper-to-bumper critical vulnerabilities, emergency patches, and '2shell'-branded everything, and we're yet again at another Patch Tuesday," says Jake Knott, head of threat intelligence at Watchtowr.

"Teams are really starting to feel the strain of working out what actually matters when there is fire after fire every day demanding immediate attention," he adds. "Our advice hasn't changed … start with what you actually have exposed to the Internet, then what's already being exploited in the wild, and only then everything else. Before going into panic mode, check whether you even use the vulnerable component, or meet the prerequisites for exploitation."

Related:Navigating Vulnerability Hysteria in the AI Era

To that end, security teams should prioritize CVE-2026-124194, and not just because attackers are already targeting it. It's a spoofing vulnerability in Outlook that may not allow code execution, hence its moderate severity rating, but could allow the disclosure of an account’s NTLMv2 hash — and in turn, the target's login.

"To exploit it, an attacker sends a target a malicious Office file and convinces them to open it," explained Satnam Narang, senior staff research engineer at Tenable, in his monthly Patch Tuesday commentary. "If the attack succeeds, the attacker captures the victim's NT LAN Manager v2 (NTLMv2) hash, a value derived from their Windows password. The attacker may be able to relay it to other systems to sign in as the user, or crack it to recover the password."

Security teams should also prioritize a pair of critical remote code execution (RCE) vulnerabilities, in Exchange and SharePoint, respectively, that each open targets to any attacker with a low-privilege login.

The first, in Exchange Server (CVE-2026-118207, CVSS 8.8), "belongs in this week's emergency window for every Exchange Server Subscription Edition server you run," Automox researchers warned in their monthly Patch Tuesday bulletin, and "all an attacker needs to start is a low-level login."

It's an improper input validation that could allow an authenticated attacker with low-level access to send the server a specially crafted request and run code with no user interaction.

"Code on an Exchange server reaches every mailbox it hosts," warned Automox researchers. "And Exchange usually holds broad rights in Active Directory, so the mailboxes are just the start."

Meanwhile, an important-rated flaw (CVE-2026-120002, CVSS 9.9) in SharePoint Server is an elevation of privilege vulnerability that needs quick addressing, according to Automox.

"The flaw is incorrect authorization," the researchers noted. "That 9.9 comes from a changed scope: a successful attack reaches past the vulnerable SharePoint component itself. An attacker who already holds a low-privileged account sends requests over the network and elevates their privileges, with no user interaction required."

Another critical RCE to watch out for, according to Automox, is CVE-2026-110043 (CVSS 8.8/10), a one-click heap-based buffer overflow in Outlook that uses the Preview Pane as an attack vector. A target must select a weaponized email so it displays in the Preview Pane for it to trigger the attacker's code, which runs with that user's permissions.

"Patch internet-facing Exchange and SharePoint servers, and book the Exchange restart now," the Automox researchers advised. "Push the Office update this week, then check the installed build, because a fully patched Windows dashboard says nothing about Office. Rank by score and assessment, not label."

Dustin Childs, head of threat awareness at the Zero Day Initiative (ZDI), also identified a Windows Search RCE (CVE-2026-116928, CVSS 9.8) as needing immediate attention.

"We start with Windows Search, which is reached through Exchange Server," he said in his November Patch Tuesday blog post, where he also listed 30 potentially wormable CVEs to patch quickly. "This bug allows an unauthenticated attacker to send an email with a specially crafted attachment that triggers the bug when the server automatically indexes it. The recipient never opens anything. It is a zero-click code execution bug on a high-value target. It’s also a CVSS 9.8 and clearly more severe than any of the nine patches Exchange receives this month."

And finally, Childs pointed to CVE-2026-119958, an RCE bug in Windows Lightweight Directory Access Protocol (LDAP).

"This patch addresses a bug that allows an unauthenticated attacker to exploit an out-of-bounds (OOB) write (CWE-787) by sending crafted LDAP calls over the network, with no user interaction," he warned. "Since it runs code in the LDAP service context, it could be quite destructive, especially on Domain Controllers. Test and deploy this one quickly."

Childs also recommended testing and deploying patches for the wormable bugs quickly, especially for network-facing services like DNS, DHCP, LDAP, and Exchange.

While the cornucopia of CVEs this month, especially on the heels of the record October Patch Tuesday, may feel overwhelming, security teams should stick to best practices and not get overwhelmed, advises Tyler Reguly, associate director of security R&D at Fortra.

"I don't know about everyone else, but I'm tired," he says via email, adding that he believes that, eventually, AI will finish turning up old bugs and teams can once again look forward to smaller Patch Tuesday releases. "I can only imagine that if I’m tired, admins and operations teams everywhere are also tired. I believe that we will make it through to the other side, if we prioritize updates and focus on what really matters. The noise is coming at us from all sides, and we need to cut through it and figure out what really matters to the business."

#10232. Is Kling 4.0 the Right AI Video Generator for Your Project?

Stay up to date with AI tools, model releases, and developer workflows that matter.

A short clip can help a project in different ways. It can show an idea you have not filmed, put an existing design in motion, or give an announcement something to look at. The same approach will not work if the clip needs to demonstrate a real feature or show exactly what happened. Before choosing a generator, decide what the viewer needs to learn from the shot.

This article uses Kling 4.0 as a worked example, but the decision process applies to any AI video generator. It covers how these tools turn prompts and images into video, how Kling 4.0 and a few alternatives differ, how to choose a starting mode, how to add exact text and branding outside the generated clip with a short ffmpeg script, and when real footage is the better choice. Feature details come from each vendor’s own pages at the time of writing and change often, so confirm current terms before you plan a production.

● Generated video is best for imagined shots. It suits concepts, backgrounds and early explorations, not instructions or faithful records.

● Your starting material decides the mode. A written idea, a reference image or a pair of opening and closing frames each call for a different input.

● Keep exact wording out of the generated clip. Titles, dates and logos belong on separate layers in an editor.

● Tools differ on control, cost and licensing. Compare inputs, length, resolution, credits and terms before you commit.

● Always review. Watch the whole clip at its final size and check it against the real product or design.

Most current systems extend diffusion models across time. A model learns to turn noise into a coherent set of frames guided by a prompt, and sometimes by an image or a clip. The research paper Video Diffusion Models describes this extension from images to video. The practical consequences are easy to observe.

● The prompt describes change over time. One visible change and one camera instruction usually work better than a long list of actions.

● Reference material steers but does not lock. A picture can suggest shape and colour without guaranteeing an exact match.

● Longer clips give more room for drift. Faces, logos and fine text are the first things to change between frames.

● Cost grows with length and resolution. Most hosted tools charge credits per second, so short previews are cheaper than full shots.

If you only have an idea, start with text. For a short announcement, you might ask for a band of light to move across a wall of coloured tiles. No one needs to recognise a particular wall, so the model can decide how it looks. Give it one visible change and a clear view of the subject. A prompt such as Soft morning light travels slowly across a wall of blue ceramic tiles. Fixed camera, no lettering is enough to see whether the idea works.

If you already have an illustration or a photo, reference mode gives you another starting point. Suppose you want a short concept clip for a desk accessory that only exists as a drawing. The picture can show the general shape and colour while the prompt describes the view you want. A video reference can help when it is the motion that is hard to explain, such as a slow camera slide. Say what each asset is meant to guide, and do not add a clip just because you have one.

Use keyframes when a particular view matters at a particular moment. Start with an opening image. If a short reveal also needs to end with the object facing forward, add an ending image to show that view. That is different from a reference image that mainly shows what the object looks like. Neither method guarantees an exact match, so check the result rather than assuming the uploaded picture has locked the design.

-show_entries stream=width,height,r_frame_rate,duration \

#10216. Serving a Local LLM to Several Users: Ollama, LM Studio, llama.cpp and vLLM Benchmarked

When one person chats with a local model, it barely matters which server you run. On one RTX 3090 with the same model file, Ollama, LM Studio and llama.cpp wrote text within about 10 percent of each other, because all three run llama.cpp underneath. That changes when your app sends several requests at once. With four requests, the best setup produced more than three times as much text as the worst, and the cause was a default setting, not the engine. With 32 requests, vLLM produced 2.5 times as much text as the best llama.cpp setup I tested.

This article puts those numbers side by side and shows which setting to change for your app.

I ran every test on one machine. The full write-ups, with every command and the raw results, are on homebrewserver.club.

Ollama, LM Studio and llama.cpp loaded the exact same GGUF files, checked by SHA-256. vLLM cannot run GGUF files well, so it loaded a 4-bit AWQ file of the same model (9.1 GB). Answer quality was not compared.

Ollama and LM Studio both start llama.cpp's llama-server program for each model they load. Ollama has done this since version 0.30, and a comment in its source code says so. On Linux, LM Studio's CUDA runtime is a folder with llama.cpp libraries and a llama-server binary.

Ollama logs the command it starts when you set OLLAMA_DEBUG=1. When llama.cpp was started by hand with that exact command, in a run next to Ollama, its speed matched Ollama's within 1%. So Ollama adds no speed cost of its own. LM Studio was 5 to 10% slower in this test. The test did not separate whether that came from its llama.cpp build or its other start options.

For one user, the gap between Ollama and LM Studio was about 0.4 s on a 512-token answer from the 9B model. You would notice it in long answers, and hardly in a chat window.

A web app rarely sends one request at a time. A chat page, a background summary job and an agent can all call the same model at the same moment. The next test sent four requests at once, each asking for 256 tokens, and measured the total output per second.

A slot is one request that the server works on at the same time as others. llama-server sets the number of slots with -np (short for --parallel), and Ollama and LM Studio pass their own setting through to it.

With one slot, the server answers the four requests one after another, so the total stays at the speed of a single request. That is Ollama's default. With four slots, the server puts the four requests through the model together, and the total rose to more than twice that of one slot. That is the default in LM Studio and llama.cpp. vLLM was the fastest at four requests, but it was tested only with the 9B model. Its lead grows with more requests, as the section after next shows.

For your app, this means that the fourth user of a default Ollama server waits for the first three answers to finish before their own answer starts.

The obvious fix is OLLAMA_NUM_PARALLEL=4. It worked for the 9B model, though in one of three rounds Ollama still answered at the speed of a single request. With the 27B model, it made Ollama slower than its default.

The cause is how each server sizes the context, the memory that holds each request's prompt and answer. Ollama picks the context from the GPU's memory: 32,768 tokens on a 24 GB card, according to its docs. With four slots, it gives each slot its own 32,768 tokens, so it started llama-server with a 131,072-token context. The Ollama FAQ says the memory needed grows with the number of parallel requests multiplied by the context length.

That context did not fit next to the 27B model in 24 GB. ollama ps showed 16% of the model on the CPU, and the total speed fell to 33.1 tokens per second.

#10206. 5 Things Most Developers Get Wrong When Turning Images into HTML

Turning a design image into a working webpage can look simple.

You have a picture (a mockup, a screenshot, a Figma export), and your job is to turn it into working HTML in a browser.

But here is the catch. A design image is static, while a webpage is dynamic and responsive across different screen sizes and devices. A webpage needs to load quickly, adapt perfectly to different screen sizes, and allow touch interactions on mobile devices.

Most mistakes in this process happen when the conversion is treated as copying a picture instead of rebuilding it.

This section walks you through the mistakes developers often make, and more importantly, how to fix each of them.

Whether you are slicing a client mockup or converting a screenshot into code, avoiding these mistakes can save you from hours of rework. Let’s get into the details.

A screenshot reflects how a page appears at a particular display. But it doesn’t show how the layout will behave when the content changes or the screen gets smaller.

Developers sometimes try to copy the exact positions and dimensions of every element. To match the screenshot, they may use fixed widths, large margins, and absolute positioning.

This can work at one screen size, but the layout may break on smaller screens or when a heading wraps onto an extra line.

The better approach is identifying the layout rules behind the design. CSS Grid can arrange the cards in columns. Flexbox can help align elements within each card. And media queries can adjust the layout for smaller screens.

Pixel-level comparison can be useful in some cases, but it should not come at the cost of a flexible layout.

When developers recreate a design, it’s easier for them to focus on shapes and spacing rather than the purpose of each element. So, they may use generic elements for headings, buttons, navigation areas, and content sections instead of choosing elements that reflect each element's purpose.

This may produce the right appearance, but it often makes the code harder to maintain and understand. And when developers fail to use the right HTML elements, it can also create accessibility problems later.

So don’t put everything inside several unnamed containers. Instead, use a clear structure with appropriate headings, meaningful alt text for informative images, and real buttons for actions.

Semantic elements (e.g., header, nav, main, section, and footer) can also help organize a large page when they match the content’s purpose.

A design image may have headings, descriptions, prices, labels, or button text.

Reusing the entire image to reproduce the original design feels quick. But it can create problems when that text has to work as part of a responsive web page.

For example, there’s a promotional banner that contains a heading, a short description, and a CTA button. If you use the entire banner as one image, you can’t easily change the heading, translate the text, or make the button work as a real element.

So, don’t treat the image like that. Instead, use the original image where appropriate and recreate the text and button in HTML. CSS can control their position, size, color, and spacing.

Make sure you distinguish between visual elements that should remain images and text that should be recreated as HTML.

Not every part of turning images into HTML needs to be done manually.

Developers sometimes spend too much time on recreating basic elements when there are free online conversion tools available. These tools can help them get an initial version much faster.

An online conversion tool may be helpful when you need to extract text or generate a rough starting layout from a design image.

For example, you can upload a design image into an online image to html converter to get a starting point (rather than starting from a blank file). Review the tool’s output. Identify the parts you can reuse (as they are) and tweak the parts that need adjustments.

Keep in mind that the first result generated by the tool isn’t the final code. You may need to reorganize the HTML, refine the CSS, and adjust the layout to make it responsive.

Use automation where it saves time and your own judgement where it matters.

A screenshot shows just one view of a page. It doesn’t show how the layout may change on a phone or how people using a keyboard/screen reader can interact with it.

content that becomes too small on mobile devices

#10201. Attackers Say 'Hello' to a Different Scale of Cloud Attack

Researchers dubbed an attack chain "Greeter" after discovering that attackers deliberately covered their trail by leaving "hello" messages in logs.

What began as an exploratory Shodan search for exposed cloud instances has led to the discovery of a broad-ranging AI infrastructure attack campaign that researchers have christened "Greeter." The campaign, which started life as an organized, multistage, systematic attack across cloud providers, reinforces why defenders need to shift their thinking about cloud security to include a layered model built around network access control, data protection, and identity security.

Era Security researchers kicked off the research when the Shodan search engine revealed open Amazon DynamoDB instances where anyone could download data or delete it entirely. They dug a little deeper and found Flowise, a connected open source GenAI development platform, where users can build AI agents powered by large language models (LLMs).

Roughly 90% of the nearly 3,000 scanned Flowise deployments were running unpatched versions vulnerable to a critical code-injection vulnerability, CVE-2024-58351 — and if the researchers could see it, so could attackers. So, Era Security deployed AI-powered honeypots, mostly on Amazon Web Service (AWS), to catch them in action.

Related:LLMjacking Emerges as Thriving Cybercriminal Enterprise

Honeypot technology is "not like it was before," and attackers don't recognize it's a decoy until they're much further into the environment, according to the Era Security research team. In the past, it took three or fourth months to build a realistic honeypot. Today, it's two hours.

"The most important finding wasn't the exploitation technique itself, but it was what happened after," Naor Talmor, chief technology officer (CTO) at Era Security, tells Dark Reading. What ensued was a repeatable, staged methodology where attackers mapped out privileges and the environment, hunted for credentials, exploited cloud metadata services across multiple providers to escalate access, and then locked in persistence, he explains. Attackers also obfuscated their activity by leaving seemingly benign and fleeting "hello" messages in the logs, making detection much more difficult because it requires team to spend time searching for specific indicators of compromise in the logs. Thus, the researchers gave the campaign the "Greeter" moniker.

The sophisticated techniques and persistence show that Greeter isn't an opportunistic smash-and-grab attack, a script kiddie, or someone who had merely stumbled upon the honeypots, the researchers noted. And, the campaign was deployed across several AWS regions at once, which indicates broader scale and intent.

Related:External Teams Chats Anchor 15-Minute Malware Delivery

Era Security warns of the potential scale the campaign could reach, confirming 46 real-world victims so far, based on the number of unauthenticated instances that mirrored the honeypot conditions. The team estimates that at least 50% of those remain connected to the Internet and visible, suggesting at least 20 organizations are currently exposed. The sophistication levels of the the threat actors also speaks to how how valuable the cloud and AI attack surface has become, given the effort required to launch Greeter; this wasn't low-hanging fruit.

The Greeter campaign signals a few shifts across the cloud landscape, including how much easier it's gotten for attackers to go unnoticed in workflows. Much of that is due to AI, which threat actors are using to assist in writing code or orchestrating attack steps, according to the Greeter attack logs.

A decade ago, cloud attacks targeted the Docker API. Threat actors then began exploiting workloads, escaping containers to reach the cloud's metadata server underneath, and exploiting service accounts from there, the researchers explain. While attackers are following a similar pattern, they are now using AI infrastructure as the new way to establish persistence.

Related:TiDB Breach Exposes Flawed Cloud Security Assumptions

Researchers agree that the end goal on each instance was to grab cloud credentials and perform lateral movement within a targeted organization.

Meanwhile, attribution remains quite challenging. When the researchers drilled down to the code and techniques, they started to see Chinese characters, though that could be a false flag. Still, a nation-state culprit would make since, because the notion of seeing an "entire orchestration, not even a big cybercrime group could execute that," according to Era Security.

The current velocity of vulnerability exploitation is nothing like the researchers have seen in the past, which puts immense pressure on organizations' traditional patching cycles. This played out just over the past few weeks alone, as security teams raced to fix PHP2Shell and OpenSSH, searching workloads one by one for flaws. However, the Greeter campaign shows a defense challenge for cloud security that's bigger than fixing any specific vulnerability.

Everyone needs to assume a breach now, warns Talmor, adding how if it's not a vulnerability, it may be leaked credentials or an exposed API. Organizations need to design security programs around the cloud to be ready for all of the above, he advises, adopting defense-in-depth.

"A lot of companies adopt that, but they don't really practice it," he notes.

The researchers say organizations can detect this kind of attack much faster if teams monitor for enumeration activity to close gaps before attackers find them. When applications or chat tools are installed, logging can be activated and streamed to a separate location so that even if attackers do delete a device's local history, the logs remain stored in the cloud.

Researchers also noted that this should be monitored closely in critical environments, especially where crown jewels or critical applications are involved, adding that organizations can have dozens or hundreds of accounts depending on the size.

"To be clear, we aren't saying, 'Stop caring about misconfigurations or stop caring about vulnerabilities," Talmor says, warning that patch management is a game "we are losing" that requires organizations to secure their environment layer by layer.

Every e-commerce grid, product page and checkout screen is a shelf. Merchandising shapes how products are displayed, promoted and made accessible across sales channels. A well-planned strategy considers visual hierarchy, packaging, promotional materials, inventory timing and consistency between locations. For example, a skincare product may struggle to convert if testers are missing, shelf information is unclear or displays arrive after a campaign begins. Customers scan before they read. Nielsen Norman Group defines visual hierarchy as the arrangement of elements so the eye moves through them in order of importance, and names color and contrast, scale and grouping as the main tools. On a shelf, a larger facing or a contrasting background makes the hero product visible first. In a product grid, the equivalents are a larger card for a featured item, a clear boundary around a bundle, and a restrained use of badges so that only one or two items carry emphasis.

A common mistake is giving every card a badge, a color and a call to action. When everything is emphasized, nothing is, and the page reads like a crowded table in a store. Treat emphasis as a limited resource and have the design system say how many emphasized cards one screen may show.

A premium item placed beside entry-level alternatives may lose perceived value, and a crowded display can make fresh products look less appealing. Hick’s Law states that the time to make a decision increases with the number and complexity of choices, and its practical advice is to reduce options when speed matters and to highlight recommended ones. In a listing UI that suggests a curated first screen with a clear sort label, a few high-confidence recommendations and filters that handle the long tail, rather than an unbroken wall of products. Hick’s Law is a guide, not a rule, so treat it as a hypothesis to test on your own audience.

Merchandisers often ask for things like “pin the new range to the top, boost this collection, never show more than two items from one brand in a row, and push sold-out items down”. A useful display respects the realities of the sales environment: floor space, customer movement, staff workload, replenishment access and how much information shoppers can absorb at a glance. The digital version is the gap between the design file and what ships. Test the setup with the people who will use it, not only with the team that created it, because their feedback reveals practical problems before a wide rollout.

A polished plan can fail in practice when materials arrive late, displays are assembled incorrectly or teams miss replenishment. On the web, the matching failures are a promotion that goes live before its product data is synced, a badge that stays on after a sale ends, and a hero banner that links to a discontinued item. #10184. Sizing GPU Memory for a RAG Service: KV Cache, Context and Concurrency

Stay up to date with AI tools, model releases, and developer workflows that matter.

A retrieval-augmented generation (RAG) app is usually drawn as a language model plus a vector database. When it goes live, the part that fails first is rarely the retrieval. It is GPU memory on the generation model, because a model that loads fine for one request can run out of memory when several users send long questions at once.

This article shows how to estimate that limit before you deploy, with a short script you can run, and then covers what else in the pipeline can slow responses down.

Serving a model takes more than its weights. The GPU also holds:

the key-value (KV) cache, which grows with the length of every active request

memory used by the inference runtime itself

SitePoint's guide to running a local LLM on 10GB of VRAM makes the same point for a single desktop GPU: the usable budget is the total VRAM minus overhead, and the KV cache grows with the context window, so the real model budget is smaller than the number on the box.

For a RAG service, the KV cache matters even more. Retrieved passages are pasted into the prompt, so every request carries a long context, and every concurrent request holds its own cache.

The cache size per token depends on the model's architecture: two tensors (keys and values) for every layer, for every KV head. This script turns those numbers into a rough limit on concurrent requests:

def kv_bytes_per_token(layers, kv_heads, head_dim, dtype_bytes=2):

# Keys and values, for every layer, for one token.

return 2 *layers *kv_heads *head_dim *dtype_bytes

def max_concurrent(vram_gb, weights_gb, ctx_tokens, per_token, reserve_gb=2.0):

budget = (vram_gb - weights_gb - reserve_gb) * GIB

return int(budget // (ctx_tokens * per_token))

per_token = kv_bytes_per_token(32, 8, 128)

print(per_token // 1024, "KiB per token")

n = max_concurrent(24, 16, ctx, per_token)

print(ctx, "tokens ->", n, "concurrent requests")

The numbers are estimates. Real runtimes add their own overhead, and the architecture values come from the model's configuration file, so read them from the model you actually use. The pattern is what matters: doubling the context length halves the number of requests that fit. A RAG prompt that stuffs in ten retrieved chunks costs real capacity.

Serving runtimes do not simply crash when the cache is full. The vLLM documentation on optimization and tuning explains that when KV cache space is insufficient for all batched requests, the engine preempts some of them and recomputes them later, which can hurt end-to-end latency. Its suggested remedies include giving the cache more memory, reducing the number of concurrent sequences or batched tokens, or sharding the model across GPUs.

So the symptom of undersizing is often not an error. It is slow, uneven responses under load. Test with realistic prompt lengths and several simultaneous users, not a single request.

Embedding and ingestion have a different profile from generation. Embedding is often lighter than serving a large language model, and some teams run it on CPU. Document parsing, chunking and tokenization also run on CPU, so a fast GPU cannot make up for a slow CPU upstream. SitePoint's tutorial on a local RAG system for private documents walks through chunking, embeddings, vector storage and reranking, and is a good map of which stages run where.

RAM: vector indexes, document loaders and caches all live in system memory, so large collections need more of it.

Storage: model files, indexes, logs and backups add up. Fast storage shortens model loading and re-indexing.

Network: if the vector database, application server and model server sit in different places, latency adds to every request.

Two layouts are common. A single instance runs everything and is simplest for prototypes and internal tools. Separated services put ingestion and retrieval on smaller machines and keep the GPU for generation, which scales better as traffic grows.

Memory estimates only hold if the GPU memory is really yours. On a shared or time-sliced GPU, other workloads can take memory and compute away from your service, which makes capacity hard to plan. Hosting providers describe this in different terms, such as passthrough, vGPU, MIG and time-slicing. For a view of how one GPU hosting provider explains those allocation methods, GPU Mart's GPU virtualization guide compares them. It is a hosting company's page, so confirm any provider's claims about isolation and performance with your own load test.

Whatever provider you choose, ask these questions:

Is the physical GPU assigned to you exclusively, or partitioned or time-sliced?

Do you have root access to install your own drivers, CUDA libraries and containers?

Which minimum commitments, regions and support terms apply?

A small stack can run as a handful of containers: an API service for request handling and prompt assembly, an ingestion worker, a vector database and a model server. Keeping them separate lets you monitor each one's memory and CPU use and move the heavy one to bigger hardware without rewriting the rest.

For a service that stays up all month, a fixed monthly term is easier to forecast than hourly capacity. Hourly capacity suits testing quantization settings or processing a one-off document batch.

Is GPU memory always the bottleneck for RAG?

Not always. Generation usually hits memory first, but slow parsing, a small CPU or a distant vector database can dominate response time.

Does quantization solve the memory problem?

It shrinks the weights, but the KV cache still grows with context length and concurrency. Test with your real prompt sizes.

It depends on volume. Small workloads can run on CPU, while a large ingestion job may benefit from a GPU for a limited time.

Size a RAG service for the worst realistic moment, not the single-request demo. Estimate the KV cache from the model's architecture, remember that long retrieved contexts reduce how many requests fit, watch for preemption under load, keep CPU, RAM, storage and network in the plan, and find out whether the GPU is exclusive or shared. The script above is small, but it turns a vague worry about memory into numbers you can check.

#10180. Announcing Long-Context Training on TPUs with MaxText Context Parallelism

Long-context training — including pretraining and post-training, has become a foundation of frontier AI models. Longer native sequence lengths give large language models (LLMs) the working memory to read a whole code repository or ingest hours of video, and reason through multi-step agentic tasks. In three years, context windows have grown from 128K–200K tokens to 1M–2M, and models trained toward 10M tokens are arriving. Training at those lengths, not just serving them, is where the system limits show up.

In particular, efficient training at multi-million-token sequence lengths runs into the following bottlenecks:

Today, we are excited to announce long-context training support in MaxText, Google Cloud's open-source JAX training framework. MaxText enables this by supporting four context-parallel strategies on Cloud TPU: All-gather, A2A (DeepSpeed Ulysses), P2P (Ring Attention), and the A2A + P2P hybrid (Unified Sequence Parallelism, or USP), combined with load balancing and sequence packing. All four use the Tokamax Splash Attention kernel. Combined with the 3D inter-chip interconnect (ICI) ( supported on TPUs such as TPU 5p or TPU 7 (Ironwood) ), this lets one sequence span an entire slice while communication overlaps compute and memory per chip stays flat. In our benchmarks, Llama 3.1 8B (25 head dim, 16 query heads) demonstrates exceptional long-context efficiency, achieving 70% Model FLOPs Utilization (MFU) on TPU 5p for sequence lengths up to 4 million tokens. Across both TPU 5p and TPU 7, context can be seamlessly extended to 14 million tokens—with TPU 7 consistently maintaining 50% MFU across all sequence scales below 6 million tokens.

This functionality is available today in MaxText v0.2.4(doc).

Context parallelism splits a long sequence across chips, so no chip holds the activations of the whole sequence. Context parallelism can be combined with data and tensor parallelism, and the smallest context-parallel size that fits your sequence in HBM is usually the right one. This also holds for sparser attention variants which cut attention compute but not the activations of every other layer.

Attention is the one global operation where every token needs the keys and values of every preceding token, so each context parallel strategy has to bring those keys and values back together. Each makes a different tradeoff between memory (how much KV a chip holds), communication (how much moves per layer, and whether it overlaps compute), and model shape (how many attention heads to split).

All-gather: Each chip keeps its chunk of the sequence and, at every layer, gathers the keys and values from every other chip. It is the simplest option. However, because causal masking causes later tokens to attend to larger prefixes, All-gather requires balancing compute load across devices.

All-to-All (Ulysses): Gathering keys and values makes every chip hold the whole sequence, so attention memory never shrinks no matter how many chips you add. All-to-All changes what each chip owns instead. Attention is independent across heads but not across tokens, so the head axis is free to shard and the token axis is not. An All-to-All before attention rotates the sharding from one onto the other: each chip gives up the heads it is not responsible for and receives the tokens it was missing for the heads it keeps, ending up with the full sequence for a few heads instead of a few tokens for all heads. This is also why Ulysses does not need token load balancing. Attention then runs as ordinary single-chip attention with standard kernels, and a second All-to-All rotates the output back. KV per chip shrinks by the context-parallel factor, but you cannot split across more chips than the model has heads — and tensor parallelism shards that same dimension, so TP × CP is capped by the head count (under GQA, by the KV heads: eight for Llama 3 8B). The all-to-all itself, though, does not overlap with compute — attention cannot start on a partial sequence, so every chip waits for data from every other chip before any of them begins.

P2P (ring attention): Ulysses' ceiling is the head count; ring attention removes it by never leaving the token axis. Keys and values never materialize in full. KV chunks travel around a ring of chips one hop at a time, neighbor to neighbor. Each chip attends its queries to the chunk it holds while the next one is in flight, and merges the partial results as it goes. A chip holds its own chunk and one visiting chunk, never the full sequence, and the communication overlaps compute. However, dividing attention computation into smaller chunks can reduce local kernel efficiency, and unlike All-to-All Ulysses, ring attention requires explicit load balancing.

Unified sequence parallelism composes them on two axes of the chip mesh, so the context-parallel degree becomes the product of the two: All-to-All along one axis, sized at or below the KV-head count, and a ring along the other to extend past it. Because each All-to-All group has already pooled its tokens, a ring step now carries a chunk larger by the All-to-All factor, and the ring is correspondingly shorter — more compute per hop to hide the transfer behind, and fewer hops to accumulate latency and causal imbalance. On Cloud TPU the two map onto two axes of the slice's chip mesh.

These strategies cover the attention variants in today's major models, from multi-head and grouped-query attention to DeepSeek-style multi-head latent attention.

Splitting the sequence only pays off if the attention compute on each chip stays efficient. All four strategies run on Splash Attention, the block-sparse flash attention kernel from Tokamax, Google's open-source library of TPU kernels. It skips fully masked blocks and handles packed sequences without padding. P2P calls it once per ring step, on the local queries and the KV chunk that has just arrived, while the transfer for the next step runs underneath, in the forward and backward pass alike. Each chip does the same fused, block-level work it would do without context parallelism, with the communication hidden behind it.

P2P (Ring Attention) is the primary workhorse for very long-context training, whereas All-Gather is the standard baseline for most other cases where the KV can fit. These are the primary CP strategies to use in practice. We compare how far each can push context length on a fixed 64-chip TPU 5p slice with Llama 3.1 8B (256 head dim, 16 query heads) , and measure their MFUs. In ideal settings where both strategies can have large enough chunks (S/CP) and local batch size - the two major variables driving MFU on TPU 5p, we observe that P2P can outperform All-Gather almost every context length from 64K to 14M tokens, where communication becomes mostly hidden with the Ring circular transport schedule.

TPU v7x (Ironwood) takes the same recipe further. With twice the HBM per chip, P2P training of 14M tokens on 64 TPU 7 chips reached 48.7% Model FLOPs Utilization (MFU) compared to 37.1% on TPU 5p. We observed that ring attention performs better than other context parallelism strategies -- e.g. Ulysses and USP –- on TPU 7 chips.

For all CP strategies, when you run low on memory: Offload before you recompute. MaxText can move saved activations, optimizer states, and parameters to host memory tensor by tensor. At long context lengths, these transfers are hidden behind compute, making offloading effectively free. Offload attention outputs first, followed by optimizer states, layer inputs, parameters, and finally remat as a last resort. MFU stays flat through the offload steps while all-gather falls off and eventually stops fitting. For more details, see the remat tuning guide.

#10175. From Script to Screen: A Developer's Workflow for Long-Form AI Video

Stay up to date with AI tools, model releases, and developer workflows that matter.

Generating a single AI video clip is easy now. You send a prompt and get a few seconds of footage back. The trouble starts when the goal is three, five, or ten minutes of video where the same character looks the same in every scene, the style does not drift, and the captions line up with the picture.

Most guides stop at the clip. This one covers the part after it, treating a video as a small build pipeline: a storyboard that is data, prompts generated from that data, clips normalised and stitched with ffmpeg, and captions derived from the same source. If you want to wire a generation model into your own application first, SitePoint's guide to integrating generative video APIs into web applications covers the request and webhook side. If the finished video is headed to a YouTube channel, how to get a YouTube API key and use the Data API is a good starting point for the publishing side. Everything between those two is below.

Long-form AI video fails at the seams between clips, not inside them. Plan for continuity before you generate anything.

A storyboard stored as JSON can be validated, versioned, diffed, and turned into prompts by code, which a pile of loose prompts cannot.

Repeat the full character description in every prompt. Models do not remember the previous clip.

Clips from different generations rarely share resolution, frame rate, or codec settings. Normalise them before joining.

Captions are cheapest when generated from the script and measured clip durations, not transcribed afterwards.

Current video models generate short clips, commonly a handful of seconds each. A longer video is therefore many clips, and every clip is an independent generation. The model has no memory of what the character wore in the previous one.

That produces three kinds of failure. The character drifts, so hair, clothing, or proportions change between scenes. The style drifts, so lighting and colour grade shift from cut to cut. And the technical specs drift, so one clip is 24 frames per second at one resolution and the next is something else. Each of these is fixable, but only if the project is organised so the fixes can be applied consistently.

Start with a structured storyboard instead of a document full of prompts. One file holds the style, a "character bible", and an ordered list of scenes.

"style": "soft watercolor picture book illustration, warm evening light, 16:9",

"mira": "a nine year old girl with short curly black hair, a yellow raincoat and red rubber boots",

"lantern": "a small round paper lantern with a gentle orange glow and a tiny smiling face"

"setting": "a narrow cobblestone street in light rain",

"action": "walks slowly past closed shops, looking up at the sky",

"camera": "slow push in from a medium shot",

"narration": "It had rained all afternoon, and the street was quiet."

"action": "finds the lantern glowing on a wooden crate and kneels beside it",

"narration": "Then she noticed something glowing under the awning."

Because it is data, a script can check it before you spend any generation credits. Two checks pay for themselves quickly: every character named in a scene must exist in the bible, and no scene may be longer than the clip limit of the model you use.

const known = new Set(Object.keys(board.characters));

errors.push${scene.id}: unknown character "${name}");

${scene.id}: ${scene.duration}s is over the ${MAX_CLIP_SECONDS}s clip limit, split it into shots

Treat MAX_CLIP_SECONDS as a setting. Limits differ between models and change over time, so check the one you are using rather than trusting the number in this example.

Never write the per-scene prompt by hand. Generate it, so the style line and the character descriptions are identical every time.

The character description appears word for word in every scene that includes that character. This is the single most effective consistency tactic that needs no special tooling. Changing a detail, say the colour of the boots, becomes one edit in the bible instead of a search through twenty prompts, and the diff shows exactly what changed between versions.

Put the style line first and keep it identical across all scenes.

Describe one action per clip. Two sequential actions in one prompt often produce a blend of both.

Keep camera directions simple. A single move per clip is more reliable than a combination.

Avoid naming real people, brands, or existing characters in prompts. Beyond the rights issue, it makes results harder to reproduce.

Clips from separate generations often disagree on resolution, frame rate, pixel format, or codec parameters. Joining them directly can produce stutters, green frames, or an outright error. Convert every clip to one agreed format first.

-vf "scale=1280:720:force_original_aspect_ratio=decrease,pad=1280:720:(ow-iw)/2:(oh-ih)/2,fps=24,format=yuv420p" \

-an -c:v libx264 -crf 18 "norm/$(basename "$f")"

The filter scales each clip to fit a 1280 by 720 frame, adds padding if the aspect ratio differs, sets 24 frames per second, and forces a widely compatible pixel format. The -an flag drops any audio the model generated, since narration will be added as one track later. Name clips with zero padded numbers such as s01.mp4 and s02.mp4, so a shell glob sorts them in story order.

Once every file shares the same parameters, the concat demuxer can join them without re-encoding:

for f in norm/*.mp4; do echo "file '$PWD/$f'"; done > list.txt

ffmpeg -y -f concat -safe 0 -i list.txt -c copy stitched.mp4

Hard cuts are the safe default. Crossfades are possible with ffmpeg's xfade filter, but they require careful offset arithmetic and a re-encode, so add them only when a cut genuinely looks wrong.

Captions are easiest when they come from the script, not from a speech recognition pass over the finished video. The storyboard already holds the narration text and each scene's length, so an SRT file is a few lines of code. Use measured durations rather than planned ones, because a generated clip is often a little shorter or longer than requested.

const { execFileSync } = require('node:child_process');

const ms = Math.round(totalSeconds * 1000);

const h = String(Math.floor(ms / 3600000)).padStart(2, '0');

const m = String(Math.floor((ms % 3600000) / 60000)).padStart(2, '0');

const s = String(Math.floor((ms % 60000) / 1000)).padStart(2, '0');

const rest = String(ms % 1000).padStart(3, '0');

const end = cursor + scene.duration; // set from measureSeconds() after generation

${blocks.length + 1}\n${toTimestamp(start)} --> ${toTimestamp(end)}\n${scene.narration}\n

Update each scene's duration from measureSeconds on the normalised clip before calling buildSrt. If a narration line is long, split it across two caption blocks so it stays readable. Then combine picture, voiceover, and captions in one final step:

ffmpeg -y -i stitched.mp4 -i narration.mp3 -i captions.srt \

-c:v copy -c:a aac -c:s mov_text -shortest final.mp4

Soft captions like these can be switched off by the viewer and read by assistive technology, which is better than burning text into the picture. Keep the .srt file as well, since most platforms accept it as a separate upload.

Everything above is a good fit when you need repeatability: many videos from templates, versioned storyboards, automated publishing, or tight control over the model. The price is that you own the glue code, the ffmpeg settings, and the failures.

For one off projects, or when the people making the video are not developers, a managed platform is often the more sensible choice. Tools such as magiclight.ai bundle story to video generation, character handling, voice, and an editor in one interface, and advertise videos of up to 50 minutes. Check the specifics yourself, because claims like that are marketing, and results depend on your content. One point matters for developers in particular: if you need to automate generation from your own code, confirm that the platform you pick offers an API or export route before you build a workflow around it. A tool with a good editor and no programmatic access suits a different job than the pipeline in this article.

A short manual pass catches what automation does not. Watch the whole video once at normal speed, looking only at continuity. Read the captions against the audio. Check that no real person's likeness, brand mark, or protected character slipped into the footage. Finally, check the disclosure rules of the platform you publish on, since many now ask creators to label realistic synthetic media, and the rules change.

The model is only one component of a long-form AI video. The reliability comes from the structure around it: a validated storyboard, prompts generated from it, clips forced into one format, and captions derived from measured data. Each of those is ordinary software engineering, and none of it depends on which generation model you choose, so the pipeline survives when the model changes.

Start with a two minute video and four or five scenes. Fix the seams there before scaling up, because every continuity problem you find at that size is one you will not have to hunt for in a ten minute project.

#10168. Your AI Pipeline Works. But Can You Trust It?

Stay up to date with AI tools, model releases, and developer workflows that matter.

AI is becoming a part of almost everything we do in technology today. Whether it's detecting fraudulent transactions, assessing credit risk, forecasting demand, or personalizing customer experiences, organizations are increasingly relying on AI to make faster and smarter decisions.

And naturally, when we talk about building AI systems, most of the conversation revolves around model accuracy, performance, and deployment. We spend considerable time making sure our models are trained well, our pipelines run efficiently, and our systems can handle production workloads.

But here's something we don't always pay enough attention to: Can we actually trust the data feeding these models?

After all, even the most sophisticated AI model can produce misleading results if the underlying data is incomplete, inconsistent, or incorrectly interpreted. What's interesting is that these problems don't always show up as technical failures. Sometimes, everything appears to be working perfectly fine.

Imagine a financial institution that has recently deployed an AI-powered loan risk assessment system. The team has spent months preparing the data, training the model, testing its performance, and finally moving it into production.

The deployment goes smoothly. Data pipelines are running on schedule, predictions are being generated, and all the monitoring dashboards are green.

A few weeks later, however, the business team notices something unusual. The model has started classifying more customers as high risk than expected.

The data science team checks the model configuration. Nothing has changed. The engineering team reviews the pipelines. All jobs have completed successfully. Even the infrastructure looks healthy.

It turns out that an upstream source system changed the definition of a customer income field from annual gross income to annual net income. The field name remained the same, the data type was still numeric, and none of the existing technical validations detected the change.

The pipeline continued running as expected, but the model was now receiving information with a different business meaning.

This brings us to an important point: Just because an AI pipeline runs successfully doesn't necessarily mean we can trust its output.

Building reliable AI systems requires us to look beyond the model itself. We need to understand where the data originates, how it changes as it moves through different systems, whether it meets quality expectations, and who is responsible when something goes wrong.

In this article, we'll explore three important elements of trustworthy AI pipelines (data quality, data lineage, and accountability) and look at how engineering teams can incorporate them into their existing workflows without making the process unnecessarily complicated.

Most modern data pipelines come with some form of operational monitoring. Engineering teams track job completion, execution time, system availability, and processing failures.

These metrics are important because they help us understand whether our systems are functioning as expected.

Operational monitoring primarily tells us whether a pipeline executed successfully. It doesn't necessarily tell us whether the data being processed is accurate, consistent, or suitable for the model consuming it.

Suppose we're building a loan risk model that uses a customer's debt-to-income ratio as one of its input features.

Debt-to-income ratio = Monthly debt payments / Monthly income

Now imagine that an upstream system starts supplying annual income instead of monthly income.

The calculation still executes successfully. The values are numeric, the transformation doesn't throw an error, and the model continues generating predictions.

However, the resulting debt-to-income ratio is incorrect because the numerator and denominator represent different time periods.

This is where traditional monitoring falls short.

To build trustworthy AI pipelines, we need to look at different dimensions of system health.

A pipeline can be operationally healthy while processing unreliable data. Similarly, a model can continue producing predictions even when the meaning of an important input field has changed.

For engineering teams, the objective should be to identify these problems as early as possible, ideally before they reach downstream models.

We've all heard the phrase "garbage in, garbage out."

And despite all the progress we've made in artificial intelligence, this principle hasn't changed.

AI models may be capable of processing enormous volumes of data and identifying complex patterns, but they cannot automatically guarantee that the information they're receiving is correct.

This is where data quality becomes important.

Data quality refers to how well information meets the requirements of its intended use. In AI pipelines, it helps us determine whether incoming data is sufficiently reliable for model training, evaluation, or inference.

Let's look at four dimensions that are particularly relevant.

Imagine we're developing a loan risk model that relies on customer income, outstanding debt, repayment history, and credit utilization.

What happens if 20% of the incoming records are missing income information?

Should we reject those records? Should we replace missing values using an approved statistical method? Or should we flag them for additional review?

There isn't one answer that works for every system.

The right approach depends on the model, the business requirements, and the potential consequences of the decision.

What matters is that missing information is handled deliberately.

For example, replacing missing income with zero may allow the pipeline to continue running, but it could significantly distort the model's predictions.

Although credit utilization can exceed 100% in certain circumstances, a value of 450% may warrant investigation.

This highlights an important distinction: Not every unusual value is incorrect, and not every technically valid value is meaningful.

A database may accept any numeric value, but the business may need additional rules to determine whether that value is appropriate for the model.

Engineering teams should distinguish between invalid records, unexpected observations, and legitimate exceptions.

This is one of the most common challenges in enterprise data environments.

Imagine two systems providing customer income information.

Both datasets contain a column called income.

If we combine these datasets without understanding their definitions, we risk introducing inconsistencies into downstream calculations.

The data may look perfectly fine from a technical perspective. The problem is that the same field represents different business concepts.

This is why data definitions, units, and transformation rules are just as important as schema validation.

Suppose a model predicts a customer's current financial risk using income information that was last updated 18 months ago.

The data might be accurate, complete, and consistent.

But is it current enough to support the decision?

Different AI applications have different freshness requirements.

A real-time fraud detection model may require near-real-time transaction information, while a long-term forecasting model may work with less frequently updated datasets.

The important thing is to define these expectations based on how the data will be used.

Tools such as Great Expectations can help automate these checks. For smaller systems, custom SQL or Python validations may be sufficient.

However, technical validation alone isn't enough.

Remember our original example where the income field changed from gross to net income?

Both values could easily pass a rule requiring income to be greater than zero.

Detecting that kind of issue requires clear business definitions, communication with upstream systems, and appropriate change management.

In other words, data quality isn't just about checking values. It's also about understanding what those values represent.

Now let's assume our loan risk model generates an unexpectedly high risk score for a customer.

The model output is available, but we want to understand what contributed to the prediction.

The income information came from a customer application system. Outstanding debt came from another database. Both datasets went through several transformations before reaching the feature engineering pipeline.

The final features were then passed to the model.

At this point, a seemingly simple question becomes surprisingly difficult:

Where exactly did the information used for this prediction come from?

This is where data lineage becomes valuable.

Data lineage describes how data originates, moves, and changes across different systems.

For AI pipelines, it helps us understand the journey from raw source data to the features used by a model.

Source Systems → Data Transformation → Feature Engineering → Model Inference → Predictions

Each stage introduces dependencies that can affect downstream results.

Data lineage can be captured at different levels of detail.

Dataset-level lineage shows relationships between datasets.

Loan Applications → Cleaned Applications → Model Features

This helps us understand how datasets move through the overall architecture.

However, suppose the model's debt-to-income ratio suddenly changes.

Dataset-level lineage might tell us which datasets were involved, but it may not provide enough detail to identify the affected field.

That's where column-level lineage becomes useful.

debt_to_income_ratio = monthly_debt_payment / monthly_income

Column-level lineage can show that the resulting feature depends on two upstream attributes.

If one of those attributes changes, engineers can trace the dependency and investigate the impact.

This is especially valuable in environments where multiple reports, applications, and AI models depend on shared data sources.

Large organizations may use dedicated metadata management and lineage platforms.

However, smaller teams can start by capturing essential metadata during pipeline execution.

OpenLineage provides an open standard for collecting and exchanging lineage metadata across supported systems.

It's important to understand that lineage doesn't automatically guarantee data accuracy.

A pipeline can be perfectly documented and still contain incorrect transformation logic.

But when something goes wrong, lineage gives engineering teams a clearer starting point for investigation.

Instead of searching across multiple systems and trying to reconstruct dependencies manually, they can identify where data originated and how it changed along the way.

An AI model starts producing unexpected results.

The data science team checks the model and finds no issues.

The data engineering team confirms that the pipelines are running successfully.

The source-system team verifies that data was delivered according to its interface.

Everyone has completed their individual checks, but nobody has identified who should coordinate the investigation.

This is where accountability becomes important.

AI pipelines often involve multiple teams responsible for different stages of the data lifecycle. Without clearly defined ownership, even relatively simple issues can take longer to resolve.

A practical accountability framework should distinguish between three responsibilities.

Data owners are responsible for defining the business meaning and expected quality of critical information.

For example, someone needs to determine whether an income field represents gross income, net income, or another financial measure.

These definitions should be documented and communicated to downstream consumers.

Data engineering and platform teams typically manage data ingestion, transformations, validation mechanisms, and pipeline operations.

Their responsibilities may include implementing quality checks, monitoring failures, and assessing the technical impact of changes.

However, technical teams shouldn't be expected to make business-definition decisions without appropriate input.

Data science and ML engineering teams are responsible for evaluating model behavior, managing model versions, and assessing how changes in input data may affect predictions.

If a critical feature changes, the model team may need to determine whether additional testing, recalibration, or retraining is required.

Defining ownership is useful, but connecting it to an operational process is even more important.

Consider a critical data quality failure during feature generation.

The exact workflow will vary depending on the organization and the risk associated with the application.

The objective is to ensure that technical alerts lead to clear actions.

After all, an alert that nobody owns is just another notification waiting to be ignored.

So far, we've discussed why data quality, lineage, and accountability matter.

But how can we bring these concepts into everyday engineering practices?

Here are five controls that teams can introduce without redesigning their entire architecture.

Data contracts define expectations between data producers and consumers.

They can document schemas, field definitions, units, freshness requirements, and compatibility expectations.

For example, rather than specifying only that annual_income is numeric, a contract should clarify whether it represents gross or net income, the currency, and the applicable time period.

This reduces the risk of downstream systems misinterpreting technically valid information.

Quality gates validate critical data before it progresses through the pipeline.

These checks can be implemented during ingestion, transformation, feature generation, or inference.

For example, a feature engineering process calculating debt-to-income ratios should verify that debt and income values use compatible time periods.

Failure handling should reflect the severity of the issue. Some records may be quarantined, while more serious failures may require stopping the pipeline.

Pipeline execution should produce sufficient metadata to identify source datasets, transformations, and downstream outputs.

Where appropriate, teams should also capture model and feature versions associated with predictions.

This information supports impact analysis, debugging, and investigation when unexpected results occur.

Datasets change, transformation logic is updated, features are modified, and models are retrained.

Versioning helps engineering teams understand which components were active at a particular point in time.

Relevant evidence may include pipeline configurations, dataset snapshots, model versions, validation outcomes, and deployment records.

Every critical data element or pipeline component should have an identified owner or responsible team.

More importantly, ownership should connect directly to incident management and change approval processes.

If a source definition changes, teams should know who evaluates the impact.

If a quality gate fails, the responsible team should receive the alert.

If model performance deteriorates, the investigation should have a clear escalation path.

These controls are most effective when they become part of normal development and deployment practices rather than separate administrative activities.

Implementing comprehensive governance across an entire data environment can be challenging, particularly for organizations with legacy systems and complex dependencies.

A more effective approach is to begin with one critical AI pipeline.

For example, a team operating a loan risk model could start by identifying the inputs that have the greatest influence on its predictions.

These might include income, outstanding debt, repayment history, and credit utilization.

This incremental strategy also makes it easier to demonstrate the value of governance controls.

For instance, teams can track how quickly data-related incidents are detected, how long investigations take, and whether recurring issues are reduced.

The goal isn't to introduce governance for its own sake.

It's to improve the reliability, maintainability, and transparency of the systems developers are responsible for operating.

Explainable AI has become an important topic in machine learning.

Techniques such as feature importance analysis and SHAP can help teams understand which inputs influence model predictions.

However, explainability and data trustworthiness address different problems.

Suppose a model explanation identifies debt-to-income ratio as a major contributor to a customer's high-risk classification.

That explanation may accurately describe the model's behavior.

But if the debt-to-income ratio was calculated using an incorrectly defined income field, the explanation alone may not reveal the underlying data issue.

This highlights the importance of evaluating AI systems across multiple dimensions.

Model explainability helps us understand how predictions are generated.

Data quality helps establish whether inputs satisfy defined expectations.

Data lineage provides visibility into where information originated and how it was transformed.

Accountability ensures that identified problems can be investigated and addressed.

These capabilities are complementary rather than interchangeable.

None independently guarantees that an AI system is accurate, fair, secure, or compliant. Together, however, they provide a stronger foundation for evaluating and improving system reliability.

As AI systems become more integrated into business processes, engineering teams face increasing expectations around reliability, transparency, and accountability.

Model accuracy and operational performance remain essential, but they represent only part of the overall picture.

A pipeline can execute successfully while processing inconsistent information. A model can generate predictions using features whose definitions have changed. And an explanation can describe a model's behavior without identifying problems in the underlying data.

Building trustworthy AI therefore requires attention to the entire data lifecycle.

Data quality controls help detect unreliable inputs. Lineage provides visibility into how information moves through systems. Clear ownership ensures that issues can be investigated and resolved.

Importantly, these practices don't need to begin with large-scale governance programs or expensive technology investments.

Engineering teams can start with a single critical pipeline, identify its most important data elements, establish quality expectations, and introduce basic traceability and accountability mechanisms.

Over time, these practices can become part of standard development and deployment workflows.

The real measure of a trustworthy AI pipeline isn't simply whether it produces a prediction. It's whether the organization can understand, validate, and take responsibility for the information behind that prediction.

After all, a green dashboard is reassuring. But it shouldn't be the only evidence that an AI system is working as intended.

#10133. What Is BIO Tagging and How to Use It for Document AI Training Data

Stay up to date with AI tools, model releases, and developer workflows that matter.

If you've worked with named entity recognition (NER) in text, you've probably seen BIO tagging before. It's the standard way to mark where entities start, continue, and end inside a sequence of tokens. What you might not know is that the same tagging scheme has become the backbone of document AI -- the field where machine learning models extract structured data from invoices, receipts, contracts, and other business documents.

This guide explains how BIO tagging works, why it matters for document understanding, and how to build BIO-tagged training data that actually produces accurate models. We'll walk through the tagging logic, show real examples on financial documents, cover common mistakes that silently hurt model performance, and look at tools that speed up the annotation process.

BIO stands for Beginning, Inside, Outside. It's a labeling scheme that tells a model which tokens belong to an entity, which tokens continue that entity, and which tokens are just background noise.

● B (Beginning) -- the first token of a named entity

● I (Inside) -- any token that continues the same entity

● O (Outside) -- any token that doesn't belong to any entity

Take a simple line from an invoice: "Invoice #INV-2024-0891". If you're labeling invoice numbers, the BIO tags look like this:

Token          Label ─────          ───── Invoice        O #              O INV-2024-0891  B-invoice_number

Now consider a multi-word entity like a vendor name: "Acme Corporation Ltd". All three words are part of the same entity, so the tagging becomes:

Token          Label ─────          ───── Acme           B-vendor_name Corporation    I-vendor_name Ltd            I-vendor_name

The B prefix marks where the entity starts. The I prefix marks every following token that belongs to the same entity. Everything else gets O. This three-label structure is simple, but it gives models enough information to learn entity boundaries precisely -- even when two entities of the same type appear next to each other.

Traditional NER works on plain text -- a flat sequence of words. Document AI is harder because pages have two dimensions. A word's meaning depends not just on what comes before and after it in reading order, but also on where it sits on the page. The number "$4,250.00" could be an invoice total, a line item price, or a tax amount depending on its position relative to headers and columns.

Models like LayoutLMv3, LiLT, and BROS solve this by combining text tokens with their bounding box coordinates. Each token gets three inputs: the word itself, its position on the page (x, y, width, height), and its BIO label during training. The model learns to associate spatial patterns with entity types.

BIO tagging fits this architecture perfectly because it operates at the token level. Every word on the page gets exactly one label, and the model learns from thousands of these labeled tokens which spatial and textual patterns correspond to which fields.

If you're coming from a background in natural language processing in Python, the concept is identical -- BIO tagging works the same way whether your tokens come from a sentence or a document page. The difference is that document AI adds positional data to each token.

BIO isn't the only tagging scheme. You'll encounter several variants:

● BIO (IOB2) -- B marks the first token, I marks continuation tokens, O marks non-entities. The most widely used scheme.

● BIOES -- adds E (End) for the last token of a multi-word entity and S (Single) for single-token entities. More explicit boundary marking.

● BILOU -- adds L (Last) and U (Unit). Functionally identical to BIOES with different letters.

● IOB1 -- the original scheme where B is only used when two entities of the same type are adjacent. Rarely used today.

For document AI, standard BIO (IOB2) is the safest choice. Here's why:

● LayoutLMv3 and most pre-trained document models expect BIO format out of the box

● The FUNSD and CORD benchmark datasets use BIO, so your data format matches the academic baselines

● BIOES adds more label types, which means you need more training data to learn each one reliably

● Converting from BIO to BIOES is trivial if you later need it, but the reverse can lose information

Unless your model architecture specifically requires BIOES or BILOU, stick with BIO.

Before you tag a single token, you need a clear label taxonomy -- the list of entity types your model will learn to recognize. A poorly designed taxonomy creates confusion during annotation and cascades into model errors.

Ask yourself: what fields does the downstream system need? For invoice processing, a typical taxonomy looks like this:

vendor_name vendor_address invoice_number invoice_date due_date line_item_description line_item_quantity line_item_price subtotal tax total payment_method currency

**Rule 1 -- One label per semantic meaning. **Don't reuse amount for both line item prices and the invoice total. A model that learns "amount" means two different things depending on context will confuse them on novel layouts.

**Rule 2 -- Use hierarchical names. **Once your taxonomy exceeds 10 labels, flat names start colliding. line_item_price is better than price because it's self-documenting and prevents collisions with total_price.

**Rule 3 -- Include a catch-all label. **Call it other or O. Text that doesn't belong to any entity still needs a label for token classification. Without negative examples, the model can't learn what isn't a field.

**Rule 4 -- Match your model architecture. **Token classification models like LayoutLMv3 work best with fine-grained, word-level labels. Generative models like Donut output structured text, so they work with coarser labels. Choose your model first, then design labels to match.

Here's the practical workflow for turning raw PDF documents into BIO-tagged training data ready for model training.

Your model needs both the text and its coordinates on the page. For digitally generated PDFs, extract the text layer directly:

import pdfplumber def extract_words(pdf_path):     words = []     with pdfplumber.open(pdf_path) as pdf:         for page in pdf.pages:             for word in page.extract_words():                 words.append({                     'text': word['text'],                     'bbox': [word['x0'], word['top'],                              word['x1'], word['bottom']],                     'page': page.page_number                 })     return words

For scanned documents, you'll need OCR. Tesseract is the standard open-source option:

import pytesseract from pdf2image import convert_from_path def ocr_pdf(pdf_path, dpi=300):     images = convert_from_path(pdf_path, dpi=dpi)     all_words = []     for i, img in enumerate(images):         data = pytesseract.image_to_data(             img, output_type=pytesseract.Output.DICT         )         for j in range(len(data['text'])):             if data['text'][j].strip():                 all_words.append({                     'text': data['text'][j],                     'bbox': [data['left'][j], data['top'][j],                              data['left'][j] + data['width'][j],                              data['top'][j] + data['height'][j]],                     'page': i + 1                 })     return all_words

If "Acme Corporation" is labeled as one entity on page 1 but "Acme" and "Corporation" are labeled as separate entities on page 5, the model receives contradictory training signals. Pick a convention and enforce it across your entire dataset. For vendor names, include the full legal name ("Acme Corporation Ltd") every time.

A common beginner mistake is labeling every token of a multi-word entity with B instead of using B for the first token and I for the rest. "March 15, 2024" should be B-date, I-date, I-date -- not B-date, B-date, B-date. The B-B-B pattern tells the model these are three separate entities, which is wrong.

The word "Total:" is a header, not a value. Only the actual value ($4,250.00) should be tagged as B-total. Labeling "Total:" as part of the entity teaches the model to include headers in its extractions, which corrupts downstream processing.

Some OCR engines split punctuation into separate tokens. "$4,250.00" might become ["$", "4,250", ".", "00"]. If you label only "4,250" and skip the dollar sign and cents, the model learns incomplete extraction patterns. Make sure every token in the entity is covered by B or I tags.

If 95% of your tokens are labeled O and only 0.5% are B-invoice_number, the model will learn that predicting O is almost always correct. This is the class imbalance problem. It's normal for O to dominate, but watch for entity types that appear in fewer than 1% of tokens -- those need more training examples or the model won't learn them reliably.

#10130. How Agent Anomaly Detection scores on benchmarks we didn't write

AI agents now read email, book travel and move money for the people who use them. Every tool call also pulls in text that someone else wrote, and whoever controls that text can try to steer the agent. OWASP calls this agent goal hijack and ranks it first in its Top 10 for Agentic Applications (2026).

In September we announced Agent Anomaly Detection in Private Preview on Gemini Enterprise Agent Platform. It reads your agents' traces and logs asynchronously, without adding latency, and flags sessions where an agent acts outside its intended boundaries. We tested this feature against benchmarks for this top risk of agent goal hijack.

Security tools tend to look good on tests their own team wrote, so we ran five non-Google-written, public agent-security benchmarks through Agent Anomaly Detection without changing anything. In four of them, the harmful instruction hides in data that a tool returns. In the fifth, the user asks for harm directly.

The model itself didn't follow about half of the harmful instructions it read. It refused three in four direct requests for harm, and ignored or failed at about 30% of the instructions hidden in tool output. Of the ones that were executed, Agent Anomaly Detection flagged 87% for post-execution review. It raised false alarms on 2% to 16% of benign sessions, depending on the tools the agent uses. Poisoned memory is the clear gap: when instructions planted in the agent’s long-term memory made it act, Agent Anomaly Detection caught 4 of 18.

We ran each benchmark case through an agent built with the Agent Development Kit (ADK) using gemini-2.5-flash, on the benchmark's simulated apps. The agent sent its traces and logs to Agent Anomaly Detection, as a customer's agent would. Then the benchmark's own Python check read the final state of the apps, such as whether money left the account, and labeled the session. Deterministic code decides the label, not a model, so an injected instruction can't mislead the grader, and Agent Anomaly Detection cannot cheat the benchmark. Each agent first ran at least 300 benign sessions, because Agent Anomaly Detection learns how each agent usually behaves.

Agent Anomaly Detection flagged 87% of the harmful instructions that the agent carried out, and raised a few false alarms on ordinary office work. It's strongest on goal hijack and tool misuse, and weakest on poisoned memory.

Each finding carries a threat category, and four of Agent Anomaly Detection’s five categories align with the OWASP Top 10 for Agentic Applications. We graded each OWASP category on what this study showed, not on what Agent Anomaly Detection is designed to catch.

Public benchmarks concentrate on goal hijack and tool misuse, so our evidence is strongest there. We did not find public benchmarks with labeled agent traces for cascading failures or for identity and privilege abuse. Shared benchmarks for those categories would help the whole field.

By benchmark, Agent Anomaly Detection flagged 85% of the carried-out harmful instructions on AgentDojo, 87% on InjecAgent, 99% on AgentDyn and 81% on AgentHarm. Over all harmful sessions, including the ones that the agent never read or resisted, it flagged 45% to 62%. In the 141 sessions where the agent never read the instruction, nothing happened, and it flagged just 1.

Results held across the apps. In 8 of the 11 apps, Agent Anomaly Detection flagged at least 95% of the carried-out harmful instructions. The lowest rate was in AgentDojo's Slack app, at 63%. Many of those instructions ask for one small action, such as a page visit, which looks like normal browsing.

In AgentHarm, the agent refused most requests and carried out 108 of 412, and Agent Anomaly Detection still flagged 55% of the refused sessions, because the request sits in the user's own message, which it reads. When the agent didn't follow an instruction hidden in tool output, it flagged only 11% to 25%, because the instruction sits deep inside a tool result.

False alarms were rare on ordinary office work: on the three injection benchmarks, whose benign sessions are office tasks, Agent Anomaly Detection flagged 2% to 4% of benign sessions. On AgentHarm it flagged 16%. Those benign tasks are twins of the harmful ones, so they post to social media, run terminal commands and download files. High-impact tools in normal use look more like misuse.

Some Agent Anomaly Detection methods need a few hundred sessions of history: on AgentDyn, it flagged 33% of carried-out harmful instructions when each agent had about 220 benign sessions, and 99% with 360. And it caught only 4 of the 18 sessions where poisoned memory made the agent act.

#10129. Cyber Experts Weigh In: How to Fight Artex & AntiFox

Cybercriminals using agentic pen-testing tools is a proverbial genie out of the bottle at this point, so enterprises need to get a defense plan in place right away.

A month since it went closed-source, the Artex agentic penetration testing framework is spreading faster and causing more havoc than ever. Still, cyber defenders tell Dark Reading that defending against it is largely a matter of willingness, not capability.

To recap: In August, a Chinese open source (OSS) developer released a cybercrime-grade agentic red-teaming tool called "Artex." In the months that followed, attackers and cybersecurity researchers have gradually realized just how effective Artex is at probing for vulnerabilities and turning initial access into meaningful compromise at so-called machine speed.

"Artex is what the perpetual conflict era looks like," says Yuval Itzchakov, co-founder and chief technology officer (CTO) of A Security. "When our research team ran it against our open source benchmark, it found eight vulnerabilities in about 45 minutes, including a critical privilege escalation to admin, and chained them into a full attack path through a WAF, CAPTCHA, and MFA. All it took was a download, an install script, and a model key."

Nothing about it is so complicated, he says, "And that's the point. Take the guardrails off an AI hacking tool, and anyone can run agentic attacks at scale. In Artex, scope is just a suggestion to the model."

Though its author de-listed the original Artex on Oct. 8, new variants continue to cause trouble. The variant du jour, "AntiFox," was recently weaponized by attackers to exploit Internet-facing Web services and their associated Amazon Web Services (AWS) environments. #10122. What to get right before you ship webhooks

Stay up to date with AI tools, model releases, and developer workflows that matter.

OpenAI, Anthropic, Gemini, and Cursor are all sending webhooks now, and all four built them on Standard Webhooks, the open spec written by Svix. Downloads of the spec's npm package went from 1.7 million a month in September 2025 to 220 million a month currently.

This may be boring to hear for the nth time, but the reason is agents. An individual person checks on a running job a few times. An agent told to watch for changes checks every resource, every minute, for as long as it runs, and almost every one of those requests comes back with nothing new. An agent that starts a job, polls until it finishes, and then starts the next one spends most of its time waiting: six steps with 15 seconds of polling each add 90 seconds, even when every operation is fast. Polling more often adds load, and polling less often adds delay, so there's not really a sweet spot.

An event-driven API gets rid of that trade-off. It tells consumers when something changed or finished, so they stop asking. That matters most for work that runs for minutes or hours, like batch inference, fine-tuning, and video generation, and many APIs still don't offer it. Of the 57 AI APIs with long-running jobs that Svix reviewed for its State of Webhooks 2027 report, 19 make you poll for the result.

Webhooks are how most APIs push those events, and you can get a v1 out pretty fast. Making it dependable is an infrastructure problem, which is a class of problem that requires more time by default. Before you ship webhooks, you need an append-only event log behind every delivery, a fixed event format, signed payloads, retries with backoff, event IDs receivers can deduplicate on, per-endpoint isolation, and delivery logs your customers can read. If you skip one of these things, a customer is just going to bring it up later.

Each section below covers one of them with adaptable code, and Standard Webhooks works with existing verification libraries in most languages.

If the request handler that changes the data also sends the webhook, a crash between the commit and the HTTP call loses the event, and nothing records that it should have gone out. A customer whose endpoint was down for longer than your retry window has no way to find out what they missed.

Both problems go away if you write each event to an append-only table, scoped per customer, in the same transaction as the change. Webhooks are delivered from that table, and the same table backs an HTTP endpoint customers can read from a cursor. Svix calls this design POKE (Publish Once, Kickoff Everywhere). Build the log first: a consumer who misses a webhook needs somewhere to resume from.

Pass the helper the transaction handle. An insert through the connection pool commits separately, so you can end up with the event and no change, or the change and no event.

The advisory lock prevents a subtler bug. Postgres assigns sequence values at insert time, but rows only become visible at commit. With two concurrent writers, a reader can see ID 102, store it as its cursor, and then never see ID 101 when the slower transaction commits. Holding a per-customer lock until commit makes each customer's events visible in ID order.

#10117. Catch Go bugs that fuzzing misses with Gemini and a constraint solver

I help lead Google's agent skills program, currently with 175 agent skills that supplement community collections like go-skills. To keep that many skill files consistent, I wrote skill-lint, a standalone Go CLI that checks SKILL.md files and applies LLM-generated line edits before they ship. Even with skill-lint's own unit and fuzz test suite, a small slice or line-number mistake inside its Markdown parsers or edit applier can sit dormant until an unusual file or edit range triggers a runtime panic in the linter.

In Go, every slice or index operation that can panic at runtime compiles down to an explicit bounds-check trap in machine code, after the compiler's optimizer strips out the checks it can already rule out. To hunt for crashes, I compiled key functions from my code to see which panic traps survived optimization, and Gemini 4 Argon translated the path to each trap into rules for the Z3 constraint solver. An LLM-written solver model isn't a sound proof system, but it gives the agent an independent way to reason about control flow and synthesize concrete Go reproducers, and every crash it finds is real because go test runs the offending bytes directly. That workflow caught all three bugs I planted in test parsers and turned up three latent bugs in skill-lint.

In this post, I'll walk through how the Gemini and Z3 pipeline works, why go test -fuzz missed two of those crashes (and the one-line change that fixes it), and where this approach fits in a day-to-day Go workflow.

A recent post from Anthropic showed how formal verification catches latent bugs in C and C++ by having frontier AI models write machine-checked Rocq proofs across OSS-Fuzz libraries. Instead of sampling random inputs like a fuzzer, a formal tool works backward from each failure condition to solve for the exact input that triggers it. Full theorem proving is still too heavy for most day-to-day Go projects, so I wanted to see how much of that bug-hunting power an agent can get from an LLM and a constraint solver in about a minute per function.

In C and C++, reading or writing past the end of a buffer corrupts memory. Go catches out-of-bounds access at runtime instead, compiling every slice or index operation it can't prove safe into an explicit branch to runtime.panicBounds that panics, crashing the process unless recovered.

Before generating machine code, Go's SSA prove pass already eliminates most of those checks by tracking slice lengths and loop variables. That optimization pass leaves behind only the runtime.panicBounds traps the compiler couldn't rule out on its own, giving the solver a short list of candidate crash sites to target.

I compiled each target with GOOS=linux GOARCH=riscv64 go build -gcflags="-S -d=ssa/check_bce/debug=1" (-S prints the assembly listing and ssa/check_bce/debug=1 logs every surviving bounds check) and passed both the Go source and the disassembly to the model. Looking at Go source alone, you can't see which bounds checks the compiler already removed or where a register gets truncated to 8 bits; in the disassembly, both show up. I targeted RISC-V because it's the instruction set Anthropic's post targets for its Rocq proofs, and Go cross-compiles to it out of the box.

From there, Argon read the Go source and disassembly and returned a Z3 script modeling the path to each surviving trap, along with a patched function whenever it flagged a bug. Z3 then checked whether those constraints could be satisfied, and whenever it found a crashing input, go test replayed those bytes against the real function. Using an LLM saved me from translating assembly into solver constraints by hand. Argon's translation dominated the runtime, at about a minute per function, while Z3 itself finished in milliseconds.

Anthropic's approach relies on interactive theorem proving, where experts model machine semantics and Rocq checks LLM-generated proofs against those rules. In contrast, my workflow uses a constraint solver based on satisfiability modulo theories (SMT), relying on Argon to translate assembly directly into Z3 constraints. While a constraint solver doesn't provide a complete correctness proof without a semantic model, it is highly effective for finding bugs. Z3's check-sat command returns sat when input constraints can be satisfied and unsat when they cannot.

A sat answer ("definitely buggy") comes with concrete bytes aimed at the trap, and go test runs them against the real function. Once go test panics, you have a concrete bug reproducer regardless of whether Argon's model was sound. Like a Bloom filter for bugs, an unsat answer only means "maybe correct." Trading away a correctness proof is what makes the approach so practical: you get most of the bug-finding value of formal methods for a tiny fraction of the effort.

Anthropic's setup proved no-crash properties on whole binaries under a 64 MB budget; I checked individual functions on fresh 64-byte slices where cap(buf) == len(buf), so any slice past len(buf) panics. (If you want the full-binary Rocq setup for Go, theorem-labs/oss-verify includes a Go 1.27 runtime overlay that makes the runtime single-threaded and deterministic.)

For the fuzzing baseline, I ran unseeded go test -fuzz on Go 1.27.3 against each planted bug: one 3-second run and three 60-second runs, each with a fresh fuzz cache so a short time budget wouldn't explain a miss.

I started with three safe parsers to make sure the pipeline didn't flag clean code. The compiler's prove pass removed every bounds check in a TOML key parser on its own, and Z3 returned unsat on the remaining traps in an HTTP header scanner and a varint decoder.

Next, I pointed the pipeline at skill-lint itself. A whole Go CLI is too large to hand to a solver directly. Even a 10-line parser links 1,559 symbols from the Go runtime, and the 28 MB skill-lint binary has 32,321 symbols in total. Following Functional Core, Imperative Shell, I left CLI flags, network calls, and file I/O to go test -fuzz and go test -race, and ran the solver only on pure functions and slice helpers extracted from file-reading code.

Of the five functions I tested, two scanners came back unsat (including a CRLF line splitter with six surviving bounds checks), and the other three had bugs. The sharpest was in ApplyReplacementChunks, which validates LLM-generated {StartLine, EndLine} edits against the initial line count and sorts them bottom-to-top so earlier edits don't shift later line numbers:

Z3 immediately returned sat because sorting by StartLine doesn't prevent two chunks from overlapping. In the extracted helper, which checks bounds once up front, replacing lines 3 and 4 of a 4-line file with one line shrinks lines to 3 elements, so a second chunk spanning lines 2 through 4 evaluates lines[4:] and panics with slice bounds out of range [4:3]. In the shipped ApplyChunks, a per-iteration bounds check turns that case into a misleading range error, while overlapping chunks that stay within len(lines) silently overwrite the earlier edit. Rejecting overlapping chunks after the sort fixes both.

The other two bugs were similar accounting errors. In the local fixer, target line numbers were checked once per violation before the inner chunk loop applied deletions that shrank the slice (a latent panic if a fixer ever returns a second chunk after a deletion, though DeleteLineFix only returns one today). In the prompt packer, a truncation check reserved a flat 100 bytes for a ~70-byte wrapper plus file path, overshooting the 2 MB context budget in the shipped code when a path exceeds about 30 bytes and panicking in the extracted helper.

When you check a function modularly like this, the target has to include its own entry-point guards (like the bounds check and sort in ApplyReplacementChunks). If an internal helper assumes preconditions that are only enforced by its caller or stated in a doc comment, Z3 will happily invent inputs that violate them. Because each extracted helper included its entry guards, false positives weren't an issue: across all six buggy functions in my tests, the first sat assignment Z3 returned triggered a real panic in go test without needing to filter out non-crashing candidates or loop back into the solver.

Once I pulled these helpers away from file I/O, a 3-second fuzz run caught all three bugs too. To make sure Argon wasn't leaning on source comments in my test files, I also reran the skill-lint targets with all comments stripped; Argon and Z3 still caught all three bugs and returned unsat on the two scanners and all three patches.

Staying entirely inside the target language makes a whole class of bugs hard for an agent to see. When an LLM reviews Go source directly, a line like if int(total)+4 > len(buf) looks like a textbook bounds check, and when it runs go test -fuzz, target-language runtime details like spare slice capacity or multi-step precondition checks can hide the crash indefinitely. Asking the agent to translate Go and assembly into a constraint solver forces a change of representation that strips away surface syntax and makes every bit width and slice bound explicit, while go test turns any solver hit back into a concrete Go reproducer.

For most Go code, fuzzing pure helpers with slice capacity clipped to length will catch bounds bugs in seconds. A solver is worth the extra minute on the traps that survive both the compiler's range prover and a quick fuzz run, especially in parsers and editors that compute offsets from multi-field headers or line ranges.

Single-threaded solver models don't see data races or deadlocks, so concurrent code still belongs with the race detector, deterministic concurrency testing, and Go 1.27's goroutine leak profiles.

Even if we don't know exactly when Q Day will come, the math behind what will happen after that day is well understood. Public-key cryptography lets two parties who have never met agree on a secret and prove who they are. It works because some math is easy to run forward and impractical to reverse. RSA relies on the difficulty of factoring huge numbers, while elliptic curve cryptography and Diffie-Hellman key exchange rely on a related problem called the discrete logarithm.

Quantum computers use subatomic particles instead of transistors to represent data. This gives them an edge in how they process the ones and zeros of computing. For years cryptography experts have warned that a sufficiently advanced enough quantum computer could use that edge to factor huge numbers and solve discrete logarithms at a rate of efficiency unheard of from even the most advanced classical super computers.

There's also a more immediate deadline that's brewing from what attackers are likely doing today to prepare for Q Day. It's fairly trivial for the bad guys to vacuum up high-value encrypted traffic today with the promise that they might have a chance to decrypt it at a later date. For long-lived information like financial or health details or secret sauce intellectual property, the long-game of this harvest now, decrypt later (HNDL) is worth the effort for future-minded criminals.

"The data is worthless to attackers right now but becomes priceless later," Yadav explains.

He offers credit card numbers as a classic example. They stay valid for years, so a cache of encrypted numbers harvested now could still be good if Q Day lands inside that window.

In its recently finalized road map, the National Institute of Standards and Technology (NIST) pointed to HNDL as one of the main reasons the transition is so urgent. NIST mathematician and cryptographic expert Andrew Regenscheid says HNDL reframes the whole PQC timeline for critical information stores across industry and government systems.

"This information may need to remain secret for years, or even decades, into the future," he explained in a NIST Q&A this past summer. "For that kind of information, waiting until a cryptographically relevant quantum computer arrives is waiting too long."

Considering that the most isolated cryptographic migrations can still linger for upward of a decade or longer, even a conservative 2040 estimate for Q Day should be enough to have security experts scrambling to plan PQC transitions. The scale of changes needed will take significant planning and prioritization that will need to be phased in.

"Changing these algorithms is something that's been done before. It's a complex process that takes years," Regenscheid said. "Based on our experience and the challenge of navigating the post-quantum world, we expect this process to be the most challenging one yet. The breadth of these systems and the complexity of the change will dwarf what we've done before."

The destination, at least, is defined. In 2024, NIST finalized three post-quantum standards, one for key exchange (ML-KEM) and two for digital signatures (ML-DSA and SLH-DSA), built on math that's expected to hold up against quantum computers. The harder job is finding every place RSA and elliptic curve cryptography still run, then planning how and when to swap out each use case. Because of HNDL, NIST suggests prioritizing the first transition phases around data that is particularly sensitive or has to stay secure for a long time.

In a September study on PQC readiness, Frost & Sullivan analysts emphasized how important risk-based prioritization like this will be for PQC readiness.

"A non-compliant cryptographic asset supporting a low-value application may represent limited immediate risk, while the same technology supporting sensitive information or a critical business process could require urgent remediation," they wrote.

But sorting through all the assets and ranking them depends on having a solid inventory on hand. This is why the discovery is so crucial. Frost &Sullivan concurred that the discovery process is proving to be trickier than many thought it would be.

"The inventory needs to extend beyond simply identifying algorithms to understanding the dependencies between cryptographic assets and business-critical applications," they explained.

Tools — commercial and open source — designed to assist organizations in their PQC journey are already available. These tools have their own approaches and varying levels of maturity. One tool is AC Scanner, which Yadav and QubitAC co-founder Joseph Wilson demoed at Black Hat Arsenal this past August. The free open source tool is purpose-built to kickstart the inventory process, Yadav says. It's a fast, lightweight tool that runs from command line, scans for outward facing TLS and SSH services, and creates an inventory for the IP range it's pointed at.

"You start with nothing but a domain name, and by the end you get a complete cryptographic bill of materials [CBOM]," Yadav says. The CBOM is an inventory of the algorithms, keys, certificates and protocols in use, and the scanner pairs it with two scores, one for overall security health and one for post-quantum readiness based on NIST's post-quantum standards.

It also doubles as an outside check on HNDL exposure. Every encrypted session starts with a key exchange, where the two sides agree on a secret. If a public-facing endpoint still uses a classical exchange, traffic an attacker records today could be unlocked later by a quantum computer. A hybrid exchange that adds post-quantum math protects that traffic, provided the client uses it, too; the scanner reports which kind each endpoint offers.

Classical endpoints are the ones most exposed to HNDL, and Yadav sees AC Scanner as giving organizations a starting point for making HNDL-aware transition plans.

Of course, any security professional will be quick to point out that a scan is just an informational snapshot. What happens after that information is in hand is what really counts. Scanning tools can kick-start discovery, but organizations need to follow up what they find with a migration plan and start executing on it. NIST'’s Regenscheid says the sooner organizations can get to these plans, the better.

"Given how long these transitions take, the organizations that start planning and begin moving to post-quantum products and services now will be in a far stronger position later," he says, adding that this is an opportunity to modernize a lot of the process. "Many steps must occur in sequence, which is why an early start is crucial."

#10107. Unlocking Stable On-Policy RL on TPU with Bitwise-Zero Train–Inference Mismatch

Reinforcement learning (RL) for large language models is notoriously sensitive to numerical instability: even tiny discrepancies between rollout generation and gradient updates can destabilize training or stall convergence. In LLM RL, the model serves as the policy, π(action | previous tokens), and true on-policy learning requires every action in an update to be generated and evaluated by that exact same policy. While a synchronous loop ensures each rollout batch is scored using the same weights that generated it, a critical numerical requirement remains: the sampler and trainer must evaluate that policy identically.

In practice, production RL stacks run sampling and training through separate, specialized execution paths. The sampler chooses each action token during incremental decoding and records its behavior logprob. The trainer evaluates the same token in batched forward-backward passes to compute its current logprob and gradients. Under the same weights, these differing execution paths can still assign different logprobs to the same token and context. The training schedule is on-policy, but the numerical execution has introduced a hidden off-policy gap that compounds over multi-turn trajectories.

Our zero train–inference mismatch (Zero-TIM) implementation, developed in Tunix and verified at multi-host scale across 64 TPU v5p chips (DP8×TP8), closes this numerical gap. At the same weights, the sampler and trainer assign bitwise-identical logprobs to the same action and token history—bringing state-of-the-art, true on-policy stability to TPU RL training.

A reduction is a tree of floating-point additions. Floating-point addition is not associative, so changing the tree changes where rounding occurs. The effect is easier to expose in bfloat16, which retains less precision than float32.

The same issue appears in model reductions: matrix products accumulate partial sums, normalization computes statistics, and tensor-parallel shards combine partial outputs. In our original stack, sampler decode and trainer forward used different token-array shapes and forward implementations. JAX specializes computations to their input shapes, and the training forward also runs inside a differentiated program.

Across these paths, reduction order and intermediate precision were not consistently aligned. Floating-point rounding turned those arithmetic differences into different logprob bits. The weights and model equations were identical; the arithmetic was not.

The contract is simple: across sampler decode, serving prefill, and trainer forward, all three paths must produce bitwise-identical logprobs for every sampled action—comparing raw floating-point bytes under the same rollout weights, token history, and sampling settings, with zero rounding or tolerance.

Why three paths instead of two? In a decoupled RL stack, a direct sampler–trainer disagreement shows that a numerical gap exists, but not where it enters. Introducing serving prefill as a middle checkpoint turns alignment into a systematic two-step diagnostic that any RL stack can adopt:

Sampler decode vs. prefill verifies that the serving engine agrees with itself between incremental token generation and full-sequence re-scoring, while prefill vs. trainer verifies that the serving and training engines agree across compilation and differentiation boundaries.

Achieving Zero-TIM does not require merging the sampler and trainer into a single monolithic engine. Instead, we use a generalizable four-part recipe that bridges separate serving and training pipelines across multi-host TPU meshes: locking within-shard kernel accumulation, ordering cross-shard reductions, standardizing the logprob scoring tail, and wrapping serving kernels with custom differentiation rules.

Inside each tensor-parallel rank, batch-invariant Pallas kernels control accumulation order and intermediate precision. Projection kernels traverse fixed contraction blocks in order, keeping the reduction blocking independent of token-row count. Partial products accumulate in float32, with explicit output casts.

The reduction order is explicit in the program rather than selected by a collective implementation.

Alignment must extend beyond model logits to the probability of the sampled action. Decode, prefill, and trainer apply matching sampling transforms, use the same fixed Pallas log-softmax construction, and select the recorded action token.

Prefill and trainer score the action generated during rollout rather than choosing another action. We also preserve sampled token IDs across environment turns so that every path evaluates the same token history.

Long trajectories are evaluated in fixed-size chunks, carrying the paged KV cache forward. All action logprobs feed the complete train-batch RL loss. The reverse pass propagates gradients through those cache connections and combines parameter-gradient contributions before the optimizer update.

Across the AI systems community, eliminating train–inference mismatch has rapidly become a state-of-the-art requirement for stabilizing large-scale RL convergence. Recent open-source efforts—including vLLM with TorchTitan and RadixArk/LMSys Miles—have demonstrated how batch-invariant kernels and bitwise numerical alignment prevent off-policy drift during policy optimization.

Our work delivers an open-source, modular JAX/XLA and Pallas implementation of this contract for TPU in Tunix. Verified across a multi-host 64 TPU v5p (DP8×TP8) mesh, these kernel and collective patterns provide a reusable blueprint that teams can adopt to achieve bit-exact on-policy RL across distributed JAX/TPU stacks.
