AI coding agents like Cursor, Copilot Agent, Devin, and Claude Code produce UI changes faster than most reviewers can audit in raw diff form, especially once changesets exceed 50+ files. The core problem is straightforward: these tools generate sprawling, multi-file changesets where syntactically correct code can still produce broken visual output. Reviewing AI-generated UI changes in a traditional diff viewer is not just slow; it is structurally inadequate for catching the kinds of regressions these tools introduce.

This frustration is well documented. A recurring observation in frontend communities such as r/Frontend is that reviewing massive diffs from AI agents is daunting, with the practical suggestion being to reduce prompt scope as the first line of defense. That instinct is sound, but scope reduction alone is not enough. Without a visual verification layer, regressions in layout, spacing, accessibility, and responsiveness slip through code review undetected.

This article provides a repeatable playbook that combines prompt discipline, Storybook component isolation, and Chromatic visual regression testing to make AI-generated UI diffs genuinely reviewable. The tech stack covered is Storybook 8, 9, or 10, Chromatic, and React or Vue 3. Percy works as an alternative for teams already invested in that ecosystem.

Understanding how to verify AI UI changes requires recognizing two structural problems that distinguish AI-generated diffs from human-authored ones.

AI agents tend to touch many files per prompt. A single instruction to "update the pricing card design" can result in changes across component files, style sheets, test files, layout wrappers, utility functions, and type definitions. Research on code review effectiveness (e.g., Microsoft and Google studies on review quality vs. diff size) consistently shows that PRs over 20 files see measurably lower review quality. The sheer breadth of changes makes it easy to miss a subtle but critical modification buried deep in the changeset.

The second problem is more insidious. Syntactically valid JSX or Vue template changes can produce broken layouts, misaligned spacing, or silently dropped accessibility attributes. An AI agent might restructure a flex container in a way that passes linting and type checking while shifting a call-to-action button off-screen at certain breakpoints. Reviewers cannot catch these visual regressions in a diff view. You need pixel-level comparison against a known-good baseline. Without it, spatial regressions bypass review entirely and reach production undetected.

Developers building on top of large language models routinely encounter inconsistent response structures, missing fields, hallucinated keys, and malformed JSON that breaks downstream logic. A single unexpected null where an array was expected can cascade through an application and take down an entire pipeline. The core issue: LLM outputs are, by default, untyped free text masquerading as structured data.

Two levels of structured output support differ in what they guarantee. JSON mode, available in providers like OpenAI and Gemini, guarantees that the model emits syntactically valid JSON. It does not guarantee any particular shape. The model might return {"foo": 42} when the application expected {"sentiment": "positive", "rating": 5}. Valid JSON is not the same as correct JSON.

Schema-constrained mode goes further. It enforces a declared JSON Schema at the token-generation level: the provider guides token decoding to produce output conforming to a specific structure. OpenAI supports this through the response_format parameter with type json_schema. Google Gemini offers it via generationConfig.responseSchema. vLLM provides schema-constrained decoding through its guided_json parameter. The strictness and subset of JSON Schema supported varies across providers, but the core mechanism is the same: constrain token sampling so only schema-valid sequences are generated.

Function calling (also referred to as tool calling) provides an alternative path to structured output. When a tool is defined with an input_schema, the provider forces the model to emit arguments matching the declared schema. This is Anthropic's primary structured output mechanism for Claude, which does not offer a dedicated response_format JSON schema mode. Instead, developers define a tool whose input schema matches the desired output structure, and the model returns the structured data inside a tool_use content block.

Use function calling when the application also needs to route actions based on the model's decision. Use response_format schema when the goal is purely typed data extraction. Both mechanisms benefit from the validation layer described below.

TypeScript's type system operates entirely at compile time. It erases all type information at runtime, which means a JSON.parse call returns any regardless of what interface was declared. Zod fills this gap by providing runtime type safety: it validates that a parsed object actually conforms to the expected shape, with rich error messages that pinpoint exactly which field failed and why. When an LLM returns "rating": "five" instead of "rating": 5, Zod reports the exact path, expected type, and received value. This level of detail is essential for debugging malformed LLM responses.

The zod-to-json-schema library converts a Zod schema into a standard JSON Schema object, enabling a single schema definition to drive both runtime validation and provider-level schema constraints.

This ProductReviewSchema becomes the single source of truth. The same Zod object validates LLM responses at runtime, generates the JSON Schema sent to providers, and infers the TypeScript type used throughout the application. There is no separate interface to keep in sync.

Missed cleanup functions in React useEffect are among the most common sources of memory leaks, stale-state bugs, and race conditions. Typical beginner tutorials demonstrate the happy path: fetch data, set state, render. They rarely address what happens when a component unmounts mid-flight, when a dependency changes faster than an async operation resolves, or when event listeners silently pile up across re-renders. This article provides a unified mental model for useEffect cleanup across three categories (timers, listeners, and fetch races), a reference table mapping setup to cleanup to pitfall, and a copy-paste PR review checklist that development teams can adopt immediately.

The mental model is simple: React runs the setup function when the component mounts, runs the cleanup function when the component unmounts, and on every dependency change, runs cleanup for the previous render's effect before running setup for the current render's effect. This cleanup-then-setup cycle on dependency change is the part most developers either overlook or misunderstand. It means that every effect invocation is paired with a corresponding teardown, and React guarantees that ordering. The setup function acquires resources; the cleanup return releases them. The dependency array declares which values, when changed, trigger that cycle again.

React 18's StrictMode intentionally runs each component's effect twice in development by simulating an unmount and remount: setup → cleanup → setup. Your setup function executes twice on the initial render in development. This double invocation exists specifically to surface missing cleanup logic. If a component registers an event listener in setup but never removes it in cleanup, StrictMode will produce two listeners after the simulated remount, making the bug immediately visible during development. As documented in the React docs on StrictMode (https://react.dev/reference/react/StrictMode), this behavior only occurs in development mode and does not affect production builds. However, the bugs it exposes are entirely real. A component that behaves incorrectly under StrictMode's double-mount has a latent cleanup bug that will manifest in production whenever the component remounts due to navigation, conditional rendering, or parent re-renders.

When a setInterval starts inside a useEffect that depends on a prop or state value, every time that dependency changes, React re-runs the effect. Without cleanup, the previous interval continues running. A second interval starts. Then a third. The observable symptom depends on what the interval does: a counter increments N times per tick (where N is the number of orphaned intervals), a polling callback fires multiple times per tick, or a UI animation speeds up erratically. Each orphaned interval holds a closure over stale state, compounding the problem. Under StrictMode's double-mount in development, this bug surfaces immediately as two intervals running from the very first render.

The correct pattern creates the interval in setup and clears it in cleanup. When the dependency changes, React clears the old interval before starting a new one with the updated value. This guarantees exactly one active interval at any point in time.

The same principle applies to setTimeout. Replace setInterval with setTimeout and clearInterval with clearTimeout. Store the timer ID returned by the scheduling function, then clear it in the cleanup return.

Without a matching removeEventListener in the cleanup return, every re-render (or StrictMode double-mount) attaches an additional handler. The handlers accumulate. A resize listener that updates state will trigger setState multiple times per resize event, once for each orphaned listener. This degrades performance and can cause subtle state corruption when multiple handlers race to update the same state variable.

The critical detail is that removeEventListener must receive the exact same function reference passed to addEventListener. An inline arrow function created inside the effect body produces a new reference on every invocation, so calling removeEventListener with a different inline arrow does nothing. The listener is never removed. When the reference changes, React cleans up the old listener and attaches the new one. Note that re-adding the listener on each dependency change is correct behavior: the old handler (with stale closure) is removed and the new handler (with fresh values) is attached.

Consider a search component where the user types quickly. Each keystroke triggers a new fetch. The request for "rea" might take 300ms while the request for "react" takes 50ms. The "react" response arrives first, and the UI shows the correct results. Then the "rea" response arrives, and because nothing prevented it from calling setState, it overwrites the UI with stale, incorrect results. This is a classic race condition. The slower response wins not because it is more recent, but because it resolves later. Without cancellation, there is no mechanism to tell the browser to discard an in-flight request whose results are no longer relevant.

The modern solution is AbortController. Each effect invocation creates a new controller instance. The controller's signal property is passed to fetch as an option. When the cleanup function runs (because the dependency changed or the component unmounted), it calls controller.abort(), which cancels the in-flight request. The fetch promise rejects with an AbortError. Browsers generally attempt to cancel the underlying network request as well, though the behavior varies by engine (see the Fetch spec on AbortSignal and MDN's browser compatibility tables). This guarantees that only the most recent request can successfully set state.

Calling abort() rejects the promise. This is normal, not an error condition. The catch block must distinguish AbortError from genuine network failures. Without this guard, the UI would flash an error for every intentional cancellation, or the rejection would trigger error-logging infrastructure. The standard check inspects the error's name property: if it equals 'AbortError', the catch block returns early without updating state or surfacing an error.

Note that the effect function itself is not async. An inner async function is declared and called immediately. This matters because useEffect expects its return value to be either undefined or a cleanup function. React ignores a returned promise and never registers a cleanup function from it.

A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. A data-fetching helper wraps a CMS or database call in a try-catch block that returns null on any error, whether that error is a network timeout, a 500 from the upstream API, or a genuine "record not found" response. The page component then checks for null and calls notFound().

During a transient outage, the ISR background render hits the data-fetching error path, receives null, triggers notFound(), and the resulting 404 response is cached. The previously valid, fully rendered page is gone. When the infrastructure recovers seconds or minutes later, the damage is already done. The 404 persists until the next revalidation cycle, and if the timing is unlucky, users and search engine crawlers see a 404 for up to one full revalidation interval (60 seconds in this example, but potentially hours in production configs).

Hydration is the process where React, running in the browser, attaches event handlers to server-rendered HTML and reconciles that static markup with the virtual DOM tree the client would have produced. For hydration to succeed, the HTML generated on the server must match, node by node, what the client renders on its initial pass. Any divergence triggers a hydration mismatch error.

The window object does not exist in Node.js. Because localStorage is a property of window, any direct access during server-side rendering fails. Developers hit one of two failure modes. The first is a hard crash: ReferenceError: localStorage is not defined, which kills the server render entirely. In the App Router, 'use client' components still pre-render on the server during next build, so this error fires during server pre-rendering, not in the browser. React detects the difference and throws a hydration mismatch warning. Modern web forms often depend on JavaScript for validation, interaction, and submission. Although JavaScript makes it possible to build sophisticated interfaces, relying on it for every essential function can make a form less reliable when scripts fail, load slowly, or become unavailable.

#10933. Vibe Coding to Production: A Developer’s Checklist for Building Reliable Web Apps

AI coding tools can turn a plain-English description into a working web application in minutes. They can generate interfaces, connect APIs, create database schemas, and help developers move from an idea to a functional prototype faster than traditional workflows often allow.

But getting an application to run is not the same as making it production-ready.

The security gap is measurable. In its 2025 GenAI Code Security Report, Veracode found that 45% of AI-generated code samples failed security tests by introducing vulnerabilities associated with the OWASP Top 10. The research evaluated generated code samples, not complete applications or confirmed cyberattacks. Nevertheless, it highlights an important risk: code that works can still be insecure.

Real-world investigations have raised similar concerns. A May 2026 WIRED investigation into exposed data in vibe-coded applications reported security and data-exposure problems in applications built using popular AI coding tools. These findings concern the applications examined, rather than every application developed with AI.

The lesson is not that vibe coding is inherently unsafe. It is that generating software quickly does not eliminate the engineering work required to protect data, verify behavior, and maintain reliability.

AI can accelerate implementation, but production readiness still requires engineering discipline.

Whether you are a developer using an AI coding assistant, a founder building a minimum viable product (MVP), or a team experimenting with vibe coding, this checklist will help you evaluate your application before releasing it to real users.

Vibe coding is an AI-assisted software development approach in which developers describe requirements in natural language and use AI tools to generate, modify, and debug code. Rather than manually writing every component, developers guide implementation through prompts, feedback, and iterative refinement.

This approach can accelerate prototyping, interface development, and repetitive programming tasks. However, generated code must still meet the same quality standards as conventionally written software.

Consider a customer portal. An AI tool might generate a login page, a dashboard, and a database connection in a single session. The interface could look complete while the application still lacks proper authorization checks, reliable error handling, or protection against unauthorized data access.

These gaps become more consequential when an application stores personal information, processes payments, manages business records, or serves multiple customers.

Production readiness means an application has been tested and configured to operate reliably in its intended environment. It includes security, correctness, performance, maintainability, monitoring, and recovery.

Before deployment, evaluate the application across the following areas.

One common mistake in AI-assisted development is building features before defining what they should do.

A prompt such as "Build a project management dashboard" leaves important questions unanswered. Who can create projects? Can users access another person's tasks? What happens when a task is deleted? Which fields are mandatory? How should errors appear?

When these decisions are left to the AI, the implementation may reflect assumptions that do not match the product's requirements.

Before generating substantial amounts of code, document:

Core functionality: What must users be able to accomplish?

User roles: Who can view, create, edit, or delete information?

Data requirements: Which fields, relationships, and constraints are necessary?

Technical constraints: Which frameworks, databases, APIs, and hosting environments will be used?

Failure scenarios: What should happen when a request fails or data is invalid?

Acceptance criteria: What observable result proves that each feature works correctly?

For example, a task management application might have this requirement:

A user can view and modify only the tasks belonging to projects they are authorized to access. Unauthorized requests must be rejected without revealing protected data.

This is more useful than simply asking an AI tool to "add secure task management." It establishes a behavior that developers can implement and test.

Once the requirements are documented, ask the AI to implement one coherent feature at a time. Review the output before moving to the next feature.

This makes unexpected changes easier to identify and reduces the risk of introducing multiple interacting bugs through a single large generation.

Keep the requirements in a project document and update them whenever product decisions change. The specification should remain the reference point for both the developer and the AI coding assistant.

A functional interface can conceal serious implementation problems.

AI-generated code may contain duplicated logic, unnecessary dependencies, outdated API usage, incorrect assumptions about framework behavior, or abstractions that make future changes difficult. A successful build does not establish that the application behaves correctly.

Code review is therefore essential, even when an AI tool generates most of the implementation.

Start with the code responsible for important application behavior:

Check whether functions have clear responsibilities, whether data flows are understandable, and whether dependencies are actually needed.

For JavaScript and TypeScript projects, automated linting and type checking can catch many common mistakes. However, these tools cannot prove that business logic is correct or that permissions are enforced properly.

When reviewing a change, ask the AI to explain its implementation and identify its assumptions. Then verify those explanations against the actual code and relevant documentation.

If a function is difficult to understand, simplify it or request a clearer implementation. Code that nobody on the team can confidently maintain is a liability, regardless of how quickly it was generated.

Authentication answers the question, "Who is this user?" Authorization answers, "What is this user allowed to do?"

Both are necessary for applications that protect private information or restrict access to particular features.

An AI-generated application may implement a login screen and assume the security requirement is complete. In reality, hiding a dashboard element or redirecting an unauthenticated visitor does not prevent someone from calling a protected API directly.

Every sensitive operation should enforce the relevant permissions on the server or trusted backend.

For example, an application that allows users to view invoices should verify that the authenticated user is authorized to access the requested invoice. It should not rely solely on a user ID supplied by the browser.

Test both permitted and prohibited actions. A good security test confirms not only that the correct user can access a resource, but also that other users cannot.

For applications handling sensitive data, consider an independent security review before launch.

AI-generated applications often work well with expected inputs. Real users, however, submit incomplete forms, unexpected values, oversized files, malformed requests, and repeated actions.

Input validation and error handling help prevent these conditions from becoming application failures or security vulnerabilities.

Client-side validation improves the user experience, but it should not be the only line of defense. Requests can bypass browser validation entirely.

Validate incoming data on the server, using rules appropriate to each field and operation. Enforce database constraints where applicable, and use parameterized queries or safe ORM methods to prevent SQL injection.

For file uploads, validate file types, enforce size limits, and store files using a design that prevents unauthorized access. Do not assume a filename or content type supplied by the browser is trustworthy.

Users need understandable error messages. Developers need enough diagnostic information to investigate failures.

These requirements should be handled separately.

A user-facing response might say, "We couldn't save your changes. Please try again." An internal log can record a request identifier, the relevant operation, and a sanitized diagnostic message.

Avoid exposing stack traces, database credentials, internal configuration, access tokens, or sensitive records in production responses.

Also test what happens when external APIs time out, database connections fail, or required environment variables are missing.

A production-ready application should fail predictably, protect sensitive information, and provide a clear path to recovery.

Testing is particularly important in vibe coding because generated code can appear convincing even when it implements the wrong behavior.

Asking an AI tool to generate tests is useful, but those tests must be reviewed. A test suite can pass while validating incorrect assumptions or ignoring the application's most important failure cases.

Start with critical workflows rather than trying to test every minor interface detail.

For an e-commerce application, these workflows might include account creation, product selection, checkout, payment confirmation, and order retrieval. For a business dashboard, they might include importing records, updating a customer, assigning permissions, and generating a report.

Pay particular attention to boundary conditions.

What happens when a form is submitted twice? When an API returns an unexpected response? When a database operation fails halfway through a workflow? When two users update the same record simultaneously?

These scenarios often reveal problems that a successful demonstration will not.

For applications that process transactions, test idempotency where appropriate so that retries do not unintentionally create duplicate payments, orders, or records.

A web application can feel fast during development and become sluggish when it handles larger datasets, multiple concurrent users, or slower network connections.

AI-generated code should therefore be evaluated against realistic usage patterns.

Begin with the operations most likely to affect the user experience:

Use browser developer tools and server-side monitoring to identify actual bottlenecks before optimizing.

Database indexes can improve frequently used queries, while pagination can prevent interfaces from loading thousands of records at once. Caching can reduce repeated work when the data and consistency requirements allow it.

For public-facing websites, evaluate relevant Core Web Vitals and test performance on realistic devices and network conditions.

Avoid adding caching layers, complex abstractions, or performance libraries simply because an AI tool recommends them. Every additional component introduces maintenance costs and potential failure points.

Measure first, optimize the bottleneck, and measure again.

Generated applications frequently depend on third-party packages, API services, and environment-specific settings. Each dependency expands the application's maintenance and security responsibilities.

Before deployment, inspect the dependency manifest and lockfile. Remove unnecessary packages, verify that required packages exist, and review known vulnerabilities using appropriate dependency-scanning tools.

Keep frameworks and libraries updated according to a deliberate maintenance process rather than automatically accepting every suggested upgrade.

API keys, database passwords, signing secrets, and other credentials should not be embedded in client-side code or committed to a public repository.

Use environment variables or an appropriate secrets manager, depending on the deployment environment. Restrict credentials to the permissions they actually require, and rotate any secret that may have been exposed.

Remember that a variable included in a browser-delivered bundle is not secret simply because it was originally configured as an environment variable.

Also verify that development and production environments use the correct endpoints, database connections, authentication settings, and logging configuration.

A local application that works with unrestricted development credentials may behave very differently when deployed under production permissions.

Deployment should be a controlled process, not a final experiment performed after development is complete.

A repeatable deployment process reduces human error and helps teams identify which changes introduced a problem.

For projects that support it, establish a continuous integration and continuous deployment (CI/CD) pipeline with automated checks for:

Before launch, verify that you can restore the application to a known-good state.

This includes maintaining version control, documenting deployment steps, backing up important data, and testing restoration procedures. A backup is only useful if it can be restored successfully.

Database schema changes deserve particular attention. An incompatible migration can make an otherwise successful deployment unusable. For important applications, plan migrations so that application versions can coexist safely during rollout and rollback.

Also check how the application behaves when a deployment fails, a service becomes unavailable, or a configuration change introduces a regression.

A reliable release process should make failures easier to detect, contain, and recover from.

Testing happens before release and in controlled environments. Monitoring helps developers understand how the application behaves after real users begin using it.

Without monitoring, a deployment can appear successful while users encounter failed requests, slow pages, broken integrations, or database errors.

Set alerts for failures that require action. Avoid collecting unnecessary personal data in logs, and define retention and access policies appropriate to the application.

For AI-powered features, monitor additional factors such as model response failures, latency, token usage, and output quality. An application that depends on an external AI service must account for rate limits, changing model behavior, and provider outages.

Monitoring does not prevent every failure. It makes failures visible enough to investigate and resolve.

Before releasing an AI-generated web application, use the following checklist to assess whether the essentials are in place.

Requirements: Core features, user roles, constraints, and acceptance criteria are documented.

Code quality: Important code paths have been reviewed, and unnecessary dependencies have been removed.

Authentication: Identity and session handling are implemented appropriately.

Authorization: Protected resources and operations enforce server-side permissions.

Input validation: Requests, uploads, and database operations are protected by appropriate validation and constraints.

Error handling: Failures are handled predictably without exposing sensitive information.

Testing: Critical workflows, negative cases, and regression scenarios have been tested.

Security: Dependencies, secrets, configuration, and common vulnerability risks have been reviewed.

Performance: Important queries, endpoints, and user journeys have been evaluated under realistic conditions.

Deployment: Builds and releases follow a repeatable process with appropriate quality gates.

Recovery: Backups, restoration procedures, and rollback options have been considered and tested where applicable.

Monitoring: Errors, availability, and performance can be observed after release.

Not every application needs the same level of testing or operational complexity. A personal prototype has different requirements from a financial application or a multi-tenant SaaS product.

The important thing is to identify the risks associated with the intended use and address them before exposing real users or sensitive data.

A developer does not necessarily need an external review for every small experiment. However, an independent review becomes increasingly valuable when the application handles sensitive information, processes payments, supports multiple customer organizations, or implements complex permissions.

It is also worth considering when the original developer cannot explain important parts of the generated code or when repeated AI-generated changes have made the architecture difficult to understand.

A useful review should examine more than formatting and syntax. It should evaluate application behavior, data access, authentication, security controls, error handling, deployment configuration, and maintainability.

For teams using AI to accelerate development, the goal is not to eliminate AI-generated code. It is to make sure that the resulting software meets the quality standards expected of any application entering production.

Vibe coding changes how quickly developers can move from an idea to working software. It does not remove the need to understand requirements, validate behavior, protect data, test failure scenarios, and maintain the application after release.

The most reliable approach is to treat AI as a development accelerator within a disciplined engineering process. Define the requirements, review generated code, test critical workflows, enforce security controls, automate deployment checks, and monitor the application after launch.

Start with the checklist in this article and prioritize the controls that matter most to your application's risk profile. For a deeper look at the development process, read this guide to production-ready vibe coding.

The goal is not simply to build an application quickly. It is to build one that users can trust, developers can maintain, and businesses can depend on.

The team behind NASA's six-wheeled Mars explorer tested a vision-enabled artificial intelligence system to map a safe route across the Martian surface without relying on human route planners.

The milestone demonstration took place on Dec. 8 and 10 and was led by NASA's Jet Propulsion Laboratory in Southern California. During the test, generative AI was used to select waypoints for the rover, a complex planning task that is normally handled by human experts on Earth.

"This demonstration shows how far our capabilities have advanced and broadens how we will explore other worlds," said NASA Administrator Jared Isaacman. "Autonomous technologies like this can help missions to operate more efficiently, respond to challenging terrain, and increase science return as distance from Earth grows. It's a strong example of teams applying new technology carefully and responsibly in real operations."

How Vision AI Helped Navigate the Martian Surface

For the demonstration, engineers used a form of generative AI known as vision-language models to examine existing data from JPL's surface mission dataset. The system analyzed the same images and information that human planners typically use, then identified waypoint locations so Perseverance could travel safely across difficult Martian terrain.

The work was coordinated from JPL's Rover Operations Center (ROC) and carried out in collaboration with Anthropic, using the company's Claude AI models.

Mars sits an average of about 140 million miles (225 million kilometers) from Earth. That distance creates long communication delays, making real-time control of a rover impossible. For nearly three decades, rover navigation has depended on human drivers who carefully study terrain data and plan routes in advance.

These planners design paths made up of waypoints, usually spaced no more than 330 feet (100 meters) apart, to reduce the risk of encountering hazards. The completed plans are sent through NASA's Deep Space Network, and the rover carries out the instructions on its own.

AI Takes Over Route Planning for Perseverance

During Perseverance's drives on the 1,707 and 1,709 Martian days, known as sols, the mission team shifted that responsibility to generative AI. The system examined high-resolution orbital images captured by the HiRISE (High Resolution Imaging Science Experiment) camera aboard NASA's Mars Reconnaissance Orbiter, along with terrain slope data from digital elevation models.

Using this information, the AI identified important surface features such as bedrock, outcrops, boulder fields, and sand ripples. It then produced a continuous driving path that included all necessary waypoints.

Before sending the commands to Mars, engineers ran the AI-generated instructions through JPL's digital twin (virtual replica of the rover). This step checked more than 500,000 telemetry variables to ensure the plan would work safely with Perseverance's flight software.

On Dec. 8, Perseverance traveled 689 feet (210 meters) using the AI-generated plan. Two days later, it drove another 807 feet (246 meters).

What This Means for Future Space Exploration

"The fundamental elements of generative AI are showing a lot of promise in streamlining the pillars of autonomous navigation for off-planet driving: perception (seeing the rocks and ripples), localization (knowing where we are), and planning and control (deciding and executing the safest path)," said Vandi Verma, a space roboticist at JPL and a member of the Perseverance engineering team. "We are moving towards a day where generative AI and other smart tools will help our surface rovers handle kilometer-scale drives while minimizing operator workload, and flag interesting surface features for our science team by scouring huge volumes of rover images."

"Imagine intelligent systems not only on the ground at Earth, but also in edge applications in our rovers, helicopters, drones, and other surface elements trained with the collective wisdom of our NASA engineers, scientists, and astronauts," said Matt Wallace, manager of JPL's Exploration Systems Office. "That is the game-changing technology we need to establish the infrastructure and systems required for a permanent human presence on the Moon and take the U.S. to Mars and beyond."

Managed for NASA by Caltech, JPL is home to the Rover Operations Center (ROC). The laboratory also oversees daily operations of the Perseverance rover for NASA's Science Mission Directorate as part of the agency's Mars Exploration Program portfolio.

In a new review published in Frontiers in Science, researchers warn that progress in AI and neurotechnology is moving faster than scientific understanding of consciousness. This gap, they argue, could lead to serious ethical problems if it is not addressed.

The authors say explaining how consciousness emerges is now an urgent scientific and moral priority. A clearer understanding could eventually make it possible to develop scientific methods for detecting consciousness. That breakthrough would have far-reaching consequences for AI development, prenatal policy, animal welfare, medicine, mental health care, law, and emerging technologies such as brain-computer interfaces.

"Consciousness science is no longer a purely philosophical pursuit. It has real implications for every facet of society -- and for understanding what it means to be human," said lead author Prof Axel Cleeremans from Université Libre de Bruxelles. "Understanding consciousness is one of the most substantial challenges of 21st-century science -- and it's now urgent due to advances in AI and other technologies.

"If we become able to create consciousness -- even accidentally -- it would raise immense ethical challenges and even existential risk," added Cleeremans, a European Research Council (ERC) grantee.

Consciousness, commonly described as awareness of both the world around us and ourselves, remains one of science's most difficult puzzles. Despite decades of research, scientists still lack agreement on how subjective experience emerges from biological processes.

Researchers have identified brain regions and neural activity linked to conscious experience, but major disagreements remain. Scientists continue to debate which brain systems are truly necessary for consciousness and how they interact to produce awareness. Some researchers even question whether this approach captures the problem correctly.

The new review examines the current state of consciousness science, future directions for the field, and the possible consequences if humans succeed in fully explaining or even creating consciousness. This includes the possibility of consciousness emerging in machines or in lab-grown brain-like systems known as "brain organoids."

The authors argue that developing evidence-based tests for consciousness could transform how awareness is identified across many contexts. Such tools could help detect consciousness in patients with brain injuries or dementia and determine when awareness arises in fetuses, animals, brain organoids, or even AI systems.

While this would represent a major scientific advance, the researchers caution that it would also create difficult ethical and legal questions. Determining that a system is conscious would force society to reconsider how that system should be treated.

"Progress in consciousness science will reshape how we see ourselves and our relationship to both artificial intelligence and the natural world," said co-author Prof Anil Seth from the University of Sussex and ERC grantee. "The question of consciousness is ancient -- but it's never been more urgent than now."

A deeper understanding of consciousness could have wide-ranging effects across society.

In medicine, it could improve care for patients who are unresponsive and assumed to be unconscious. Measurements inspired by integrated information theory and global workspace theory[1] have already detected signs of awareness in some individuals diagnosed with unresponsive wakefulness syndrome. Further progress could refine these tools to better assess consciousness in coma, advanced dementia, and anesthesia, and influence treatment decisions and end-of-life care.

Mental health treatment could also benefit. Understanding the biological basis of subjective experience may help researchers develop better therapies for conditions such as depression, anxiety, and schizophrenia by narrowing the gap between animal studies and human emotional experience.

Greater insight into consciousness could reshape how humans think about their moral responsibilities toward animals. Identifying which animals and systems are sentient could influence animal research practices, farming, food consumption, and conservation strategies. "Understanding the nature of consciousness in particular animals would transform how we treat them and emerging biological systems that are being synthetically generated by scientists," said co-author Prof Liad Mudrik from Tel Aviv University and ERC grantee.

Consciousness research could also affect how the legal system understands responsibility. New findings may challenge traditional legal concepts such as mens rea, the "guilty mind" required to establish intent. As neuroscience reveals how much behavior arises from unconscious processes, courts may need to reconsider where responsibility begins and ends.

At the same time, advances in AI, brain organoids, and brain-computer interfaces raise the possibility of creating or altering awareness beyond natural biological limits. While some researchers believe consciousness might arise through computation alone, others argue that biological factors play an essential role. "Even if 'conscious AI' is impossible using standard digital computers, AI that gives the impression of being conscious raises many societal and ethical challenges," said Seth.

The authors emphasize the need for a coordinated, evidence-based approach to studying consciousness. "We need more team science to break theoretical silos and overcome existing biases and assumptions," said Mudrik. "This step has the potential to move the field forward."

The researchers also argue that scientific work should place greater emphasis on phenomenology (what consciousness feels like) alongside studies of function (what consciousness does).

"Cooperative efforts are essential to make progress -- and to ensure society is prepared for the ethical, medical, and technological consequences of understanding, and perhaps creating, consciousness," said Cleeremans.

Rather than relying on many repeated reflections, the Stanford team introduced microlenses inside each cavity to tightly focus light onto a single atom. Even with fewer light bounces, this method proved more effective at pulling quantum information from the atom.

A qubit can represent zero, one, or both states at the same time, allowing quantum systems to handle certain calculations far more efficiently than classical machines.

"A classical computer has to churn through possibilities one by one, looking for the correct answer," said Simon. "But a quantum computer acts like noise-canceling headphones that compare combinations of answers, amplifying the right ones while muffling the wrong ones."

Unlike conventional synthetic materials with fixed behaviors, this smart skin can be tuned to respond in multiple ways. Its appearance, mechanical behavior, surface texture, and ability to change shape can all be adjusted when the material is exposed to external triggers such as heat, solvents, or physical stress.

The findings were published in Nature Communications, where the study was also selected for Editors' Highlights.

Sun, the project's principal investigator, said the concept was inspired by cephalopods such as octopuses, which can rapidly alter the look and texture of their skin. These animals use such changes to blend into their surroundings or communicate with one another.

"Cephalopods use a complex system of muscles and nerves to exhibit dynamic control over the appearance and texture of their skin," Sun said. "Inspired by these soft organisms, we developed a 4D-printing system to capture that idea in a synthetic, soft material."

He described the process as 4D printing because the printed objects are not static. Instead, they can actively change in response to environmental conditions.

This technique converts image or texture data into binary ones and zeros and embeds that information directly into the material. The approach is similar to how dot patterns are used in newspapers or photographs to create images.

By encoding these digital patterns within the hydrogel, the researchers can program how the smart skin reacts to different stimuli. The printed patterns determine how various regions of the material respond. Some areas may swell, shrink, or soften more than others when exposed to temperature changes, liquids, or mechanical forces. By carefully designing these patterns, the team can control the material's overall behavior.

"In simple terms, we're printing instructions into the material," Sun explained. "Those instructions tell the skin how to react when something changes around it."

One of the most eye-catching demonstrations involved the material's ability to conceal and reveal visual information. Haoqing Yang, a doctoral candidate in IME and the paper's first author, said this capability highlights the potential of the smart skin.

Yang noted that the Mona Lisa was used only as an example. The printing technique allows virtually any image to be encoded into the hydrogel.

"This behavior could be used for camouflage, where a surface blends into its environment, or for information encryption, where messages are hidden and only revealed under specific conditions," Yang said.

Looking ahead, the researchers aim to create a scalable and versatile platform that allows precise digital encoding of multiple functions within one adaptive material.

Distrust at the intermediate level stops the current attack, but it is fragile: new intermediates cross-signed under the same root would be trusted by default. Mozilla has therefore gone further and removed the eMudhra root entirely in NSS 3.131.1, and Chrome has confirmed it is removing emSign ECC Root CA - G3, the root that signed the compromised intermediates, from the Chrome Root Store, with the change reaching devices from October 27. Note also that the compromised intermediates were cross-signed by Sectigo’s AAA Certificate Services root, so a chain can build through either root - blocking only the eMudhra root path does not close the Sectigo one, which is why the incident’s official Linux workaround distrusts both roots.
