Sending a document for signature is the easy part of an e-signature integration. One POST request and the signer gets an email. The work that actually breaks in production happens afterwards: knowing when the document was signed, trusting the notification that told you so, handling the same notification twice, and getting the final PDF into storage before the download link expires.

This tutorial builds that whole loop in Node.js with Express. An event in your app (a deal is approved, a client is onboarded, a task moves to "ready to sign") sends a contract from a template. When the signer finishes, a webhook arrives, your server verifies it, and the signed PDF plus its audit trail get saved without anyone touching them.

The code uses Firma.dev, the e-signature API I work on, because I needed a real API to make the examples runnable. The patterns are not specific to it, though. Signature verification, idempotent handlers, short-lived download URLs, and reconciliation jobs show up in almost every webhook-driven integration, and the same structure applies whether you're receiving events from a payment processor, a CI system, or another signing provider.

There's a fifth part that tutorials usually skip: a reconciliation job that catches anything the webhooks missed. We'll build that too, because webhooks are a notification mechanism, not a delivery guarantee.

Before sending anything, wrap the HTTP calls in one place. This is where authentication lives, and it's also where you handle 429 Too Many Requests once instead of in every caller. Most APIs, this one included, return a Retry-After header on a 429, so the client should honour it rather than guessing a backoff.

The 503 branch matters later. When a document has just been completed, the final PDF and its completion certificate take a moment to generate, and the download endpoint says so with a 503 and a Retry-After instead of handing you a half-built file.

The trigger depends on your product. It might be a route handler, a queue consumer, or a CRM automation calling into your service. What matters is that the function doing the sending is small and takes plain data:

Two design choices are worth calling out.

Use a single create-and-send call when you can. Many signing APIs split this into "create a draft" and "send the draft." That's useful when a human needs to review the document first, but for automation it creates a window where your process can crash between the two calls and leave an orphaned draft. A combined endpoint makes the operation atomic from your side.

Store the provider's ID on your own record immediately. Webhook payloads reference the signing request, not your deal or customer. Without that mapping you'll end up searching by email address, which falls apart as soon as one client signs two documents.

Here's the first place integrations quietly go wrong. Webhook signatures are computed over the exact bytes the sender transmitted. If Express parses the body as JSON first, you lose those bytes, and re-serialising the object won't reproduce them (key order, whitespace, and number formatting can all change). Signature checks then fail intermittently, which is the worst kind of failure.

Most webhook providers sign payloads with HMAC-SHA256 using a shared secret. The details vary, so read your provider's docs for the exact header format, but the scheme here is common: the header looks like t=1731456000,v1=5f2b..., and the signed string is the timestamp, a dot, and the raw body. Stripe uses a very similar format, and the Standard Webhooks spec describes the same idea as a vendor-neutral convention.

The OWASP guidance on cryptographic storage covers the other half of this: the secret belongs in an environment variable or secrets manager, never in the repository.

Every serious webhook system delivers at least once, not exactly once. If your endpoint is slow, returns a 5xx, or the network drops the response, the sender retries. Firma.dev, for example, makes up to three attempts per event (immediately, then after at least five minutes, then after at least an hour) and treats anything other than a 2xx as a failure, including redirects. Other providers retry more aggressively. Either way, your handler will eventually see the same event twice.

Also notice the order in the route: respond with 200, then do the work. Many providers time out deliveries after a few seconds (five, in this case). Downloading a PDF and uploading it to object storage can easily take longer than that, and a timeout counts as a failure, which triggers a retry, which triggers duplicate work. Acknowledging fast and processing asynchronously avoids that loop.

setImmediate is fine for a tutorial, but it has a real weakness: if the process dies after sending the 200 and before finishing the work, the event is acknowledged and lost. Now the actual business logic. You'll usually see several event types (sent, viewed, a signer signed, declined, expired, completed). Only one of them means "the document is final":

Three things in here are easy to get wrong.

Don't treat "a signer signed" as "the document is done." With multiple signers, each one triggers its own event, and a per-signer "all complete" flag can be true on more than one of them. Key your storage logic off the single completion event.

Don't persist the download URL. Pre-signed URLs expire (this one carries an expires_at). Saving the link to your database and serving it to users later produces broken links a few minutes or hours later. Download the bytes and store them in storage you control. Swapping the fs.writeFile calls for an S3 PutObject or a Google Drive upload is a drop-in change.

Store the audit trail, not just the PDF. If a signature is ever disputed, the PDF shows what was signed, and the audit trail shows who signed it, when, and from where (timestamps, IP addresses, the sequence of views and signatures). That evidence is what makes an electronic signature defensible, which brings us to the legal side.

Retries are finite. Endpoints go down during deploys. Some providers auto-disable a webhook after enough consecutive failures, and events aren't guaranteed to arrive in order. Any one of these can leave a completed document sitting unsaved.

None of this is legal advice, but a few facts shape how you build.

In the US, the ESIGN Act and the Uniform Electronic Transactions Act (adopted by 49 states) give electronic signatures the same legal standing as handwritten ones for most commercial documents. ESIGN also has requirements around consumer consent and record retention, which is part of why you store the final PDF yourself rather than relying on a third-party link.

In the EU, eIDAS defines three levels: simple (SES), advanced (AdES), and qualified (QES). SES and AdES cover most business contracts. QES requires a qualified trust service provider and certificate-based identity, and some documents (certain property transfers and court filings, depending on the country) require it or exclude e-signatures entirely. Check which level your document types need before you pick a provider, since not every API offers every level.

Across jurisdictions, the evidence that holds up is the same: who signed, how they were identified, when it happened, and proof the document hasn't changed since. That's the audit trail and the completion certificate, which is why Step 6 stores both.

AMD says Ozaki FP64 emulation is no replacement for the real thing when it's needed.

As Supercomputing 2026 (SC26) opens in Chicago this week, AMD is indirectly needling Nvidia about the lack of native FP64 data type support in its data center GPU products. FP64, or double-precision floating-point math, is widely used in the high-performance scientific computing and simulation fields that are the focus of SC26. For those customers, AMD is trumpeting the value of its latest Instinct MI430X accelerator for customers that still need native FP64, like national laboratories and supercomputing centers.

Over the past few years, Nvidia has reallocated die area on its data center GPUs to favor the lower-precision matrix math that boosts the operations needed for much of modern AI inference. That reallocation only makes business sense, as the total addressable market for AI compute has exploded while the demand for double-precision math in large supercomputing installations has remained flat by comparison.

To make up for the lack of native FP64 support, Nvidia has turned to techniques that allow it to emulate FP64 operations using methods like the Ozaki schemes. But AMD claims this kind of emulation is nowhere close to a replacement for native double-precision processing for a few reasons—hence continued development of specialized products like the MI430X.

For one, AMD notes that Ozaki emulation assumes that the workload in question resembles a dense general matrix multiply (GEMM). In its own application profiling, the company says "less than 10%" of HPC workloads perform dense GEMM operations, so this emulation is a good replacement for native compute. Dense linear algebra is the one common workload for which AMD says Ozaki emulation is a natural fit.

For workloads like sparse iterative linear algebra, stencils and hydrodynamics, high-order finite element analysis, Monte Carlo and particle transport, and classical molecular dynamics, AMD says developers still need strong FP64 vector performance for the best results.

Furthermore, even for workloads that map well onto GEMM operations, AMD says matrix sizes must be large in order to achieve the best performance, and that might also not be a given for every operation. The operands of those matrices also have to be sized well to the hardware, as incorrectly scaled operands can reduce performance. The FP64 vector math capabilities of the MI430X are insensitive to those operand sizing issues.

Beyond those stumbling blocks, AMD also notes that using Ozaki emulation methods can cause the memory footprint of an application to balloon, requiring up to three times more capacity than native FP64 would.

Since HBM capacity is directly tied to GPUs in modern supercomputing installations, fitting a workload to a machine that can only emulate FP64 operations could have cascading effects on the number of GPUs and compute nodes required, causing knock-on challenges for the floor area, power, and cooling required to support the system.

AMD says the high 432GB of HBM4 memory capacity per MI430X node allows its customers to provision fewer GPUs and compute nodes in a system, saving on networking, power, and floor space.

In addition to its FP64 HPC performance, AMD positions an MI430X-powered supercomputer as an AI inference platform for developing workloads that utilize those models as part of the research process. But there are some key differences between those systems and the Helios rack-scale accelerator powered by MI455X GPUs from the same CDNA 5 architectural family.

Each MI430X GPU offers 9.2 PFLOPS of theoretical FP4 compute performance for inference, but that should be understood in the context of the whopping 40.3 PFLOPS of FP4 compute from each AI-focused MI455X accelerator.

Beyond raw performance, the native scale-up domain size of four MI430Xs over AMD’s Infinity Fabric interconnect when coupled with a sixth-generation EPYC host CPU pales in comparison to the domain size of 72 MI455X accelerators in a Helios rack. AMD says this interconnect is optimized more for latency-sensitive operations rather than a massive scale-up domain.

Of course, every customer and user of such a system will have different requirements, and institutional supercomputing installations usually aren’t trying to do double duty as cloud inference providers.

For scientists and engineers whose AI models of choice work well within the 1.72 TB of aggregate HBM4 capacity and 93.2 TB/s of memory bandwidth offered by four MI430X's working together across the 12.3 Tbps of scale-up bandwidth available within such a node, the inference performance of each node is likely more than up to the task of the kinds of AI applications that need to be run alongside double-precision compute workloads.

In any event, the MI430X can already count several supercomputing design wins in its corner. The upcoming Discovery supercomputer at Oak Ridge National Laboratory, the Alice Recoque installation in France, the LUMI-AI system at Finland’s CSC, and the Herder system in Germany will all take advantage of the native FP64 support offered by the MI430X.

AMD’s continued support for native FP64, even as Nvidia retreats from that capability in its products, will doubtless be a point of pride for its architects and engineers, even as those institutional supercomputers will be dwarfed by both AMD and Nvidia-powered AI inference installations the world over. The company's semi-custom silicon design chops and chiplet experience give it the flexibility needed to tailor products like the MI430X to these specialized markets instead of pursuing a one-size-fits-all approach.

#10507. Should We Look to Hunter-Gatherer Societies as Models of Equality?

Become a subscribing member today. Help us continue to bring “the science of a meaningful life” to you and to millions around the globe.

Greater Good Science Center • Magazine • In Action • In Education

On the shores of Lake Eyasi in Northern Tanzania, a small number of people still hunt and gather their food. Today a Hadza hunter has taken down an animal—a kudu. He can’t carry it by himself, so he cuts his poisoned arrow from its flank, covers the carcass in dry grass to hide it from hyenas, and heads home to enlist help.

News spreads like wildfire across the camp. Everybody rushes to the kill. They divide up the carcass, carry it back, then divvy it up some more. Every family gets some, and after the meat is cooked, there’s more sharing still. On a good day like today, the hunter and his family retain half, but sometimes they keep much less. People may even walk from other camps, and almost everyone, from miles around, is entitled to a share.

The post-hunt scene above is idyllic. It paints a quintessential picture of egalitarianism and equality. But our experience as anthropologists working with the Hadza people of Tanzania and with the Tsimane people of Bolivia’s Amazon rainforest is that inequalities are part of even the most equal of societies. Furthermore, the equalities that do exist often emerge from selfish motives.

Insights like ours are revising researchers’ understanding of both the past and how people operate today, as inequality grows globally. Hunter-gatherers are often at the center of heated academic battles about what it means to be human, including debates over gender, war, and peace and whether humans are, by nature, egalitarian or hierarchical.

Sometimes these debates oversimplify. So we pulled together hundreds of different sources covering more than a century of ethnography to find out just how egalitarian hunter-gatherer and other subsistence societies really are.

Anthropologists have called hunter-gatherers such as the Hadza “egalitarian societies,” with equalities of power, wealth, and social status. And it’s true that the traditional subsistence communities we work with successfully limit many inequalities.

Most families have similar, modest possessions and store little material wealth. When leaders do emerge, they are highly constrained in how they can direct other people. People often make decisions via consensus, and, if they cannot reach agreement, families will move away.

While the same anthropologists also emphasize that some hunter-gatherers are very unequal and that equality takes deliberate effort, the prevailing impression is that equality characterizes hunter-gatherers, past and present.

A quick trip to your local bookshop will reveal grand claims, including that past hunter-gatherer societies had no permanent leadership and no hierarchy, inequality only spread with the development of agriculture, and humans are noble by nature.

Some scientists are pushing back against these utopian portrayals. The popular bestseller, The Dawn of Everything, calls egalitarianism a “Garden of Eden narrative” that lacks substance. Other scholars have called egalitarian societies a scientific origin myth.

So where does the truth lie? Probably somewhere in between.

In our recent wide-ranging review of the evidence from the early 20th century onward, we found that no society lacked inequality.

Like the Hadza, the Ju/’Hoansi of the Kalahari desert in southern Africa had little property and widespread food-sharing, yet certain families controlled valuable hunting territory surrounding waterholes. The Bayaka of the central African rainforest had little material inequality, yet they bought, sold, and hoarded ritual knowledge. The Philippine Agta controlled and arranged their children’s marriages, hugely discriminating against orphans.

Gender inequalities were commonplace. The Tanzanian Hadza keep certain cuts of meat exclusively for older men, and give more respect to better hunters. Across societies, women have universally done more direct parenting, and men have participated more frequently in community-level decision making.

No society lacks informal leadership. Age was another source of inequality. In many Australian societies, older men controlled ritual secrets and had power over the marriage choices of younger relatives.

Our study also found that although hunter-gatherers are frequently generous, the processes limiting inequality often do not require any generosity. Instead, equality often results from people’s self-interested motives to acquire resources, status, and autonomy.

A great example of this is food-sharing. Although each Hadza family gets a cut of kudu meat, it often happens not because the hunter’s family prioritizes total equality, but because other families request it vociferously. It can involve more taking than giving, often through strongly stated demands or complaints.

Another example is ridicule and mockery of stingy or braggadocious individuals, which keeps greed and bravado in check. Paradoxically, status-seeking can also promote equality, when cooperating to gain status diffuses status throughout the community.

Many of these inequality-reducing processes are familiar to people everywhere.

Ridicule and mockery are ubiquitous in industrialized societies, from political cartoons to social media. Lampooning authority is even common in autocratic societies where governments spend large sums of money suppressing speech. Demands and complaints form the basis of strikes and collective bargaining. And key to social mobility is cooperation among people of different social strata.

Like many great debates, the truth is complex: Our ancient hunter-gatherer ancestors didn’t reach the giddy heights of inequality seen in other societies over the last 6,000 years, but putting hunter-gatherers on a pedestal as paragons of equality is a mistake. Sweeping statements about equality in the past blind us to the tools that probably allowed ancient hunter-gatherers to combat inequality, just as they and people in all societies do today.

Egalitarianism, then, is best seen not as perfect equality but as a set of tools that people use to secure their own autonomy and access to resources. Equality along one dimension or another might be the outcome, but it doesn’t rely on people being amazingly noble or completely lacking in greed or status-seeking. If you consider egalitarianism as equality-creating processes, you can see that it is a widespread reality among hunter-gatherer societies, and beyond.

The obvious test is to time 100 calls through the gateway, time 100 direct calls, and compare the two medians. That test gives the wrong answer, for two reasons.

Unlike Grace, which relies on off-the-shelf Neoverse V2 CPU cores developed by Arm, Vera uses Nvidia's proprietary Olympus cores specifically designed to maximize per-core performance as well as to ensure high aggregate throughput. To assess the computational capabilities of Nvidia's custom Olympus microarchitecture and its advantages over Neoverse V2, Nvidia's researchers used a double-precision general matrix multiplication (DGEMM) workload based on an assembly kernel from OpenBLAS, an open-source linear algebra library. Every SSL certificate comes with a limited lifespan. Following the latest update from the CA/Browser Forum, the maximum lifetime of a certificate has fallen from 398 days to 200, and it will drop to 100 days in March 2027 and 47 days in 2029. Renewal is no longer an annual chore. It’s an ongoing task that only stays manageable with automation.

So what does this mean if you already look after sites with SSL certificates, and will it bring drastic changes? For many setups, very little will change. For others, one missed renewal can mean an outage. This article explains what’s changing and what to do if you’re in the second group.

Today, an SSL certificate is valid for 200 days at most. The limit applies when a certificate is issued, so the ones you already hold keep their original expiration date.

Where you feel it depends on how your certificates renew. Sites on managed hosting platforms or behind a content delivery network (CDN) usually renew automatically already, often every 90 days, so the new limit changes little. The pressure lands on setups where someone buys a certificate once a year and installs it by hand. At 47 days, that becomes about 12 renewals a year.

A certificate is a promise from a certificate authority that a key really belongs to a domain, and that promise gets less reliable the longer it runs. If a private key leaks, or a certificate is issued by mistake, it stays usable until it expires. Cutting the lifetime shrinks that window, so a problem that once lingered for over a year is now fixed in weeks.

Shorter lifetimes also make revocation, the process for canceling a bad certificate, far less critical. Revocation has never worked perfectly, but a certificate that expires within weeks matters much less if a cancellation doesn’t reach every browser.

Another reason is about people. A task done once a year is easy to forget and hard to check from outside. Browser makers have pushed for years to move the industry onto automatic renewal, on the logic that a process that runs every few weeks gets tested constantly. If it breaks, you notice quickly instead of discovering it on the day the certificate expires.

For most people, the first effect is simply more work. A certificate that once needed attention every year will soon need it every few weeks. Plus, each renewal is a small chance for something to go wrong. Multiply that by dozens of sites, mail servers, and devices, and the chance of one slipping through grows quickly.

The safety nets are also thinner. If you relied on the renewal emails, nothing is watching your certificates now. Additionally, with a shorter life, there’s less time between this should have renewed and this has expired.

An expired certificate doesn’t make a site slow or dated. It makes it unreachable for most visitors. Chrome, Firefox, and Safari all show a full-page warning that the connection isn’t private, and most people leave instead of clicking through. If the site uses HSTS, a setting that tells browsers to connect only over secure links, there is often no way to click through at all, and visitors are blocked outright until the certificate is fixed.

The damage doesn’t stop at the home page. Checkouts, contact forms, and logins that depend on the secure connection fail along with it, often without an error message that points at the real cause. Other systems break, too, because apps and integrations that call your site over a secure link refuse to connect to an expired certificate.

Nothing about your site has to change for any of this to happen. A date passes, and a site that worked on Friday is down on Monday. In a 47-day lifetime, that date comes around about every six weeks.

#10438. Logging AI Prompts and Responses in Java Without Leaking Sensitive Data

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

Have 30-200 Employees? Make $50k-$500k selling your data for AI Training.

Stay up to date with AI tools, model releases, and developer workflows that matter.

Picture this. A customer writes to your support chatbot: "Hi, I'm Asha, my card ending 4111 was charged twice, call me on 98400 12345." Your Java service wraps that message in a prompt, sends it to a model, and logs the whole thing so you can debug it later. Congratulations, you now have a customer's name, phone number and card details sitting in a plain text log file that half the engineering team can open.

This happens more often than people admit. Logging AI calls is genuinely useful, but prompts and responses are some of the most personal text your application ever touches. Here's how to keep the usefulness and drop the risk.

A regular web request is easy to log: URL, status code, time taken. AI calls are messier.

The output changes from run to run. If a user says "your bot gave me a wrong answer yesterday", the only proof of what happened is what you sent and what came back at that moment. You can't just replay it and expect the same result.

Prompts are also built, not typed. The final text is usually a template, a few retrieved document chunks, some chat history and the user's message stitched together. When something looks off, the bug could be in any of those pieces, and only the assembled prompt shows you which one.

Then there's cost. You pay by the token, so without per-call records you can't say which feature is burning money. And quality drifts over time as models get upgraded and templates get edited. Old logs are your only baseline.

So yes, you need these logs. The real question is what goes into them.

Before writing any masking code, agree on what counts as sensitive. In most business apps that means:

Names, emails, phone numbers and home addresses

Card numbers, bank details and government ID numbers

Health, legal or job-related details people mention in free text

Internal material like contract wording, pricing rules or source code

The first three groups follow patterns, so they're easy to catch. The last two don't, and that's where most teams get caught out. Keep that in mind, because it shapes the design below.

The safest sensitive value is the one that never reaches the log. So split what you record into two buckets.

The first is metadata: a request ID, a hashed user or tenant ID, model name, prompt template name and version, token counts, latency, retry count, error type and estimated cost. None of this is personal, and it answers most day-to-day questions.

The second is content, meaning the actual prompt and response text. You only need this when you're investigating quality, and even then you rarely need all of it. A sensible default is to log metadata for every call and masked content for a small sample, maybe five percent, plus every failed call.

Here's a mistake that's easy to make: letting the log appender clean things up afterwards. By then the raw text may already be in a buffer, an async queue or a crash dump. Mask first, then log.

The cleanest way is one small component that every AI log call has to pass through:

public interface PiiMasker {     String mask(String input); }

Nothing else is allowed to write raw prompts. One chokepoint is much easier to review and test than masking sprinkled across fifty classes.

For structured data like emails, cards and tokens, regular expressions do the job well:

public class RegexPiiMasker implements PiiMasker {     private static final Map RULES = new LinkedHashMap<>();     static {         RULES.put(Pattern.compile("[A-Za-z0-9.%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}"), "[EMAIL]");         RULES.put(Pattern.compile("\b(?:\d[ -]?){13,19}\b"), "[CARD]");         RULES.put(Pattern.compile("\b(?:\+?\d{1,3}[ -]?)?\d{10}\b"), "[PHONE]");         RULES.put(Pattern.compile("(?i)bearer\s+[A-Za-z0-9.~+/=-]+"), "Bearer [TOKEN]");     }     @Override     public String mask(String input) {         if (input == null || input.isBlank()) return input;         String result = input;         for (var rule : RULES.entrySet()) {             result = rule.getKey().matcher(result).replaceAll(rule.getValue());         }         return result;     } }

A few small choices matter here. The patterns are compiled once, not on every call. The order is fixed, because a card number can otherwise get half eaten by the phone rule. And the replacement labels such as [EMAIL] keep the sentence readable, so whoever debugs it later can still follow what the user was asking.

Regex won't catch a name like "Asha Raman" or an address buried mid-sentence. For those you have a few options, and they work best together.

You can run a named-entity recognition model that tags people, places and organisations, then mask anything above a confidence threshold. You can do exact replacement of values you already know, such as the customer's name from the current session. Or, best of all, you can mask at the field level while building the prompt. If your code knows that customer.getEmail() is going into the template, swap in a placeholder right there instead of trying to spot it afterwards. Knowing beats guessing every time.

Plain redaction can remove too much. If the same email shows up five times in a conversation, five identical [EMAIL] tags hide the fact that it was one person.

The fix is consistent pseudonyms. Turn each real value into a short token using a keyed hash, so the same email always becomes something like EMAIL_7f3a. You can still follow the thread, but nobody can read the original from the log. Use an HMAC with a secret from your secrets manager. A plain unkeyed hash of a phone number can be brute-forced in minutes, because there just aren't that many phone numbers.

One warning: if you also store a lookup table to reverse the tokens, that table is now sensitive data too. Most teams are better off with one-way tokens.

Free-text log lines are hard to search and easy to leak through. Write one JSON record per AI call with clearly separate fields:

log.info("ai_call",     kv("requestId", requestId),     kv("model", model),     kv("promptVersion", "support-reply-v4"),     kv("inputTokens", usage.inputTokens()),     kv("outputTokens", usage.outputTokens()),     kv("latencyMs", elapsed),     kv("promptMasked", masker.mask(prompt)),     kv("responseMasked", masker.mask(response)));

Now dashboards for cost and latency never need to touch the text fields at all. You can also keep the two kinds of data for different lengths of time: metadata for a year, masked content for a couple of weeks. Put the request ID into your logging framework's MDC so every line belonging to one call, including retries and tool calls, carries the same ID.

Streaming trips people up. Tokens arrive in tiny pieces, and a card number can be split across two chunks, which means masking each chunk on its own will miss it. Collect the full response in a buffer, mask it once the stream ends, and log that. If the stream dies halfway, run the partial buffer through the same masker.

Tool calls are the other trap. When the model calls one of your Java methods, the arguments and return values are often the most sensitive thing in the whole exchange: order details, account balances, addresses. Treat them as part of the prompt and response. Log the tool name, duration and outcome by default, and log arguments only after masking.

Masking lowers the risk but never removes it, so surround it with some ordinary discipline:

Give content fields a short retention period. Old prompt archives are liabilities.

Limit who can read AI logs. Debugging a model doesn't mean someone needs to read customer messages.

Encrypt log storage and the pipeline that feeds it.

Log the hashed user ID so you can find and delete one person's records when they ask.

Allow verbose logging in development with fake data, and enforce strict settings in production through configuration, not through people remembering.

A masker that quietly stops working is worse than having none, because everyone assumes the logs are clean. Write tests for it:

@Test void masksEmailAndCardNumber() {     String raw = "Contact me at asha@example.com, card 4111 1111 1111 1111";     String safe = new RegexPiiMasker().mask(raw);     assertFalse(safe.contains("asha@example.com"));     assertFalse(safe.contains("4111"));     assertTrue(safe.contains("[EMAIL]"));     assertTrue(safe.contains("[CARD]")); }

Build a small set of messy, realistic samples: numbers with odd spacing, mixed languages, addresses inside sentences, text pasted from spreadsheets. Run them in your CI pipeline, and add a new case every time a leak turns up. A scheduled job that scans stored logs for patterns that should never appear makes a good safety net too.

A few I'd watch for. Logging raw text at debug level and assuming production never enables it; debug flags get switched on during incidents, so mask at every level. Masking only the user's message while forgetting retrieved documents, system prompts and tool results. Letting SDK exceptions carry the full request body into the logs. Leaving wire-level HTTP logging on in production, which bypasses your masker completely. And treating masking as finished once it ships, when every new prompt template can bring new kinds of data.

Every AI call writes a structured metadata record with a request ID

What is a unified lead tracking pipeline?

It is a workflow that converts inquiries from different channels into a shared data model, preserves their acquisition context, and connects them to business outcomes. Forms and calls keep their own interaction records, while contacts and opportunities provide the relationships needed for reporting.

Can I connect a phone call to a website visit?

Sometimes. Dynamic number insertion can provide a session or visitor association when the provider's mapping is available and valid. A campaign-specific number usually supports campaign-level attribution. If the caller uses a saved number, switches devices, or calls after a mapping expires, the available evidence may be less precise.

Handle duplicate delivery and identity resolution separately. Stable event IDs and a database constraint prevent repeated notifications from producing repeated work. Connecting several interactions to one contact or opportunity requires a separate matching policy, with ambiguous cases left unresolved until there is enough evidence.

Should a completed call count as a conversion?

Only if that is the conversion your report explicitly measures. A completed call does not establish that a prospect qualified or bought something. Keep technical call status separate from CRM outcomes and use the latter when reporting qualified demand or revenue.

Do I need a message broker for this architecture?

You can begin with PostgreSQL and an outbox worker if that setup meets your throughput and latency needs. A broker becomes useful when several consumers need independent delivery, or when buffering and scale justify the additional operations. In either case, retries still require idempotent consumers.

Keep the inquiry flow usable and apply your site's existing consent rules to optional attribution collection and storage. Accept permitted form or call data, leave unavailable attribution empty, and avoid reconstructing a visitor identity through fingerprinting. Reports should expose that missing context instead of inventing a campaign match.

If the score goes up, the change was good. If it goes down, revert. Over weeks of this, the agent inches toward the ceiling of what the model, tools, and prompt can do together. The quality-engineering name for this is hill-climbing.

The Agents CLI eval namespace was built around this loop. The commands are small and framework-agnostic: eval generate runs the agent against a dataset of cases, eval grade scores the generated traces, eval compare diffs two run results side by side, eval analyze clusters failures into themes, and eval optimize runs an automated hill-climbing pass on the agent's prompt.

A few patterns and anti-patterns from running this loop ourselves and watching teams do the same.

Lead with a small, representative dataset, not a comprehensive one. The temptation when starting an eval is to try to cover every edge case the agent will ever see. The result is a dataset that takes an hour to run and that nobody runs on a change. Four cases that run in under a minute, as above, exercise the main behaviors and get run on every change. A regression dataset of three hundred cases that runs for an hour becomes a release gate at best and shelfware at worst.

Snapshot result files, not scores. The score is a summary; the result file is the evidence. When a regression surfaces three weeks after a prompt change, having the full result JSON from before and after the change (not just the mean score) is what lets eval compare show the specific case that moved. The per-case breakdown in Step 4 above would not have been possible from scores alone.

Separate the dataset from its expectations. The dataset is the inputs. The eval config is the expectations. They evolve on different cadences: the dataset grows as new real-world cases surface in production, and the config evolves as the team's definition of "good" matures. Keeping them in separate files, both committed to version control, makes it clear which half changed when a score moves.

Treat summary metrics with suspicion. The model-swap experiment in Step 5 is the clearest example. The mean dropped by half a point, but the per-case breakdown showed the drop was concentrated in one case while the others held or improved. A team that only looked at the mean would have made the wrong call.

More evals do not automatically lead to more fixes. A recent controlled study we ran found that coding agents using agents-cli run four times as many evals as coding agents without it, but change the agent after an eval about as often as the baseline. The behavior gain comes from what the skills put into the build at the start, not from the inner iteration. Evals are necessary for quality, but the quality comes from acting on what the evals show.

The ideal UI testing tool is the one that discovers what your users discover first: broken layouts, usability issues that no longer work, and new accessibility issues in all the browsers your users use before a change goes into the repository. In 2026, most frontend teams don't rely on a single tool to do all of that. The best setups involve two layers: a test runner layer that launches the browser and monitors behavior, and a UI testing and review platform that visually checks the outcome and routes changes to the right stakeholders for sign-off.

Even with the right stack, it still relies on what your team needs to catch. Different teams will focus on different points: a QA team trying to automate checkout flows, a design system team defending shared components, and a single developer working on a tight budget will all be somewhere different. This guide is categorized by the job these UI testing tools do, then connects them.

Most "best UI testing tool" lists rank test runners and visual testing platforms against each other as if they were interchangeable. They aren't. UI testing covers four distinct jobs:

Functional testing: Does the UI respond correctly when a user clicks, types, or hovers?

Visual testing: Does the UI still look right across layout, color, typography, and spacing?

Accessibility testing: Can people using keyboards and screen readers use it, and did this change introduce new violations?

Cross-browser and device coverage: Does it work in Safari on mobile, not just Chrome on a developer's laptop?

There are also other levels of UI tests. Unit tests test the logic but don't interact with the UI. End-to-end (E2E) tests represent the full user journey in a browser but are difficult to set up, hard to troubleshoot when the bug is a visual detail, and can't practically test every state. Between the extremes of unit tests and E2E tests, component tests simulate each component's behavior in a real browser using fixed inputs, offering speed closer to unit tests and user-level coverage closer to E2E. Many teams maintain a thin layer of E2E tests for critical journeys, and they have component tests for the dozens of states a component may be in.

These tools are organized by job so you can stack them rather than choose one winner

2.     Keep a map of room names to the set of sockets in each room.

3.     When a client sends a join message, store the room name on the socket and add it to that room's set.

4.     For every other message type, forward the raw message to the other sockets in the same room, and never echo it back to the sender.

5.     On disconnect, remove the socket from its room so stale peers do not receive messages.

In production you would add authentication, limit room size to two for one-to-one calls, and validate message types, but the shape stays the same.

Both sides create an RTCPeerConnection, add their local tracks and listen for the remote ones:

1.     Create a new RTCPeerConnection with an iceServers list that contains at least one STUN server.

2.     Loop over the local stream's tracks and call addTrack() for each one.

3.     In the ontrack handler, attach the first remote stream to your remote video element.

4.     In the onicecandidate handler, send every new candidate to the other peer through your signalling channel as a candidate message.

One peer creates an offer, the other answers, and both apply each other's descriptions. Candidates arrive asynchronously in the background.

1.     The caller runs createOffer(), applies it with setLocalDescription() and sends the description as an offer message.

2.     The callee applies the offer with setRemoteDescription(), runs createAnswer(), applies it locally and sends it back as an answer.

3.     The caller applies the answer with setRemoteDescription().

4.     Both sides pass every incoming candidate message to addIceCandidate().

If both peers might start a call at the same time, look up the "perfect negotiation" pattern on MDN. It assigns one side as polite and resolves offer collisions cleanly instead of leaving both peers stuck.

On a home network, STUN alone often works. On corporate Wi-Fi, mobile carriers and symmetric NATs it frequently does not, and the call silently fails to connect. A TURN server relays media when a direct path is impossible. The open-source coturn server is the usual choice.

In practice, your iceServers list should contain your own STUN URL plus a TURN URL with a username and credential, so the browser can fall back to the relay automatically when direct connectivity fails.

Generate short-lived TURN credentials on your backend rather than hard-coding them, and budget for bandwidth: relayed calls pass every frame through your server.

Users deny camera access, unplug headsets and switch from Wi-Fi to 4G mid-call. Catch NotAllowedError and show a clear explanation, listen for devicechange events, and use RTCRtpSender.replaceTrack() to swap cameras without renegotiating the whole call.

Listen to pc.onconnectionstatechange. When the state becomes disconnected, wait a few seconds before giving up, because it often recovers. On failed, call pc.restartIce() to try new network paths.

Use RTCRtpSender.setParameters() to cap the bitrate on weak connections, and read pc.getStats() to monitor packet loss and round-trip time. Showing a small "poor connection" indicator does more for perceived quality than any codec tweak.

Mesh calls, where every participant connects to every other, work for two or three people. Beyond that, upload bandwidth explodes. Group calls need a Selective Forwarding Unit (SFU) such as mediasoup, LiveKit or Janus, which receives each stream once and forwards it to the others.

Tutorials end at a working demo, but the fastest way to understand what production WebRTC looks like is to watch a real call from the inside. Chrome ships an internal diagnostics page that shows every peer connection the browser opens, and it works on any site that uses WebRTC.

1.     Open chrome://webrtc-internals in one tab and keep it open.

2.     In another tab, start a call on your own demo and find its RTCPeerConnection entry.

3.     Expand that entry and look at the ICE candidate pairs: you will see whether the call went direct (host or srflx) or through a TURN relay (relay).

4.     Open the stats graphs for the outbound video stream and watch the bitrate, frame rate and resolution adapt when you throttle the network in DevTools.

5.     Check the negotiated codec and how quickly the connection recovers when you switch Wi-Fi off and back on.

Once you can read your own call, repeat the exercise on a production service. Any browser-based product works, whether a meeting tool or a live video chat that pairs two visitors, because webrtc-internals shows the same data for every site. Expect differences from your demo: more candidate pairs, a relay candidate in the list and a bitrate that adapts faster. Seeing them makes the earlier sections concrete, from why TURN matters to how bandwidth estimation reacts to packet loss.

The one-to-one call above is the core of many products, from telehealth consultations and tutoring to customer support. The engineering challenges grow with the use case: random matching needs queueing and presence on the signalling server, public platforms need moderation and reporting, and global audiences need TURN servers in several regions.

Start with the minimal version, get it working across Chrome, Firefox and Safari on both desktop and mobile, and add TURN before real users arrive. Once the call is reliable, every other feature becomes a much easier problem.

#10365. Cost per task: Using cheap classifiers to route across Gemini models and thinking levels

Per-token API prices keep falling, yet engineering bills for autonomous coding agents keep climbing. Price per million tokens isn't the metric that actually governs production economics anymore. The dominating metric is now cost per successful task: total spend across every loop iteration, tool call, retry and internal thinking pass divided by the number of tasks that pass verification.

When an agent calls a high-thinking reasoning configuration for every micro-decision in its harness, you're paying deep-reasoning prices for questions a lightweight configuration already answers accurately. To prevent this unnecessary overhead, consider adding a lightweight routing layer that can intercept routine decisions before they ever reach an expensive reasoning model.That is the premise behind wiring TypeSafe's Jev classifier in front of Google Antigravity's model calls. Rather than generating text token by token, Jev—a specialized structured-output classifier designed for high-throughput decision pipelines—evaluates structured classification primitives in a single forward pass: a Choice from a list, a numeric Score or a Noul, which returns a 0 to 1 probability for a binary statement.

For full disclosure, Google has no partnership with TypeSafe, and this article is not an endorsement of TypeSafe or its products. Jev is used here as one example of a lightweight classifier, and the same routing pattern can be built with other classifiers, including Google-native ones. The Getting started with discriminative models codelab, for example, runs the same kind of classifier on DiffusionGemma, Google DeepMind's open-weights model, in your own Google Cloud project.

We ran a 50-question, auto-graded, coding-agent benchmark against live Gemini and Jev APIs to test whether a near-free classifier can route each task to the cheapest model that still gets it right. Here's what we learned:

The naive way to ask Jev to route a coding task is a single broad Choice question: simple or complex. When we tested that first on 16 coding-agent tasks, Jev routed nearly everything to simple, even tasks requiring an LRU cache trace or modular exponentiation. TypeSafe's documentation warns against this exact anti-pattern. If a question weighs multiple factors or requires a meta-judgment, decompose it into an atomic check.

When we replaced the broad Choice question with one atomic Noul question, it fixed the separation immediately. The question was: does answering this require performing more than one sequential calculation, simulation step or logical deduction, rather than a single direct lookup, format check or one-step classification?

On those initial 16 tasks, Jev routed 13 of 16 in agreement with our hand-labeled difficulty on the first run and 14 of 16 on the second pass. Many engineering teams ask whether they even need a classifier API when they can write a zero-cost regex and prompt-length heuristic in Python, matching words like sequence, modulo and race condition or escalating any prompt over 35 words.

On the 16 development questions used to write those exact rules, the local heuristic scored 15 of 16, or 93.8%. To test whether that heuristic survived contact with realistic coding-agent traffic, we froze its code without changing a character and added 34 unseen held-out tasks across seven coding-agent buckets: fact extraction, schema validation, short classification, single-hop code checks, state simulation traces, math or logic chains and subtle language-semantics bugs.

On the 34 held-out questions, the frozen heuristic dropped 23.2 percentage points to 70.6%. Realistic simple tasks such as extracting a port from a Kubernetes YAML manifest, a file path from a unified git diff header or a line number from a Python traceback exceeded 35 words and triggered false escalations. Conversely, concise multi-step code traces such as mutable default arguments across calls, Python dictionary key hashing on {1: "a", True: "b", 1.0: "c"} and C short-circuit evaluation lacked the heuristic's hardcoded puzzle words and were falsely routed to the simple path. Jev classified all 34 unseen tasks with 100.0% agreement, 34 of 34, reaching 48 of 50, or 96.0%, across the full suite.

Capping the model's output at 300 tokens didn't save any money on easy tasks. The cap is only a ceiling, and easy answers never came close to it. On the easy tasks, the capped version actually cost slightly more than the uncapped one. All the cap did was break 7 of the 25 hard tasks. On six of them, the model ran out of room while still reasoning and never gave an answer. On the seventh, it squeezed its reasoning to fit, finished on time and got the answer wrong.

So a Jev router that sends easy tasks to the capped model and hard ones to normal Flash got all 50 right. It still cost slightly more than skipping the router and using normal Flash for everything, and it was slower. If your cheap option doesn't actually make the model think less on easy tasks, no router can save you money. Not even a perfect one that costs nothing.

Why it works. On its own, Flash-Lite answered every simple task in half a second but missed 6 of the 25 hard ones. Jev flagged all 6 as complex with high confidence and escalated them. That brought its cost close to what a perfect router would achieve.

Two things in our results only show up once you look past it.

Routing and caching pull in opposite directions. Our test prompts were short, standalone tasks, and on those the Jev router helped reduce both cost and response time. Real coding agents often look different. They send the same big block of context on every turn, such as a map of the repository and the tool definitions. Agent Platform Context Caching stores that block so you pay 75% to 90% less to resend it. The catch is that a cache belongs to one model. If your agent switches between Flash-Lite and Flash from turn to turn, it either keeps two caches or loses the discount. The practical split: route short, self-contained tasks like log parsing or schema checks, and keep long, context-heavy turns on one model.

Match the model to the workload. Gemini 3.1 Pro is built for deep, multi-step reasoning, and it brings that same depth to every request, including short lookups that don't need it. For a workload made mostly of quick checks and extractions, a Flash configuration is the better fit, and Pro is best saved for the tasks that need its reasoning depth. Model configurations can also apply different safety settings to security-related prompts. In our run, the Pro configuration declined two short code-security review prompts that Flash answered. If your agent performs security reviews, test those prompts on the configuration you plan to use.

Other ways to build the router. Jev is one way to get a fast classifier, but not the only one. The Getting started with discriminative models codelab runs the same Choice, Score and Noul questions on DiffusionGemma, Google DeepMind's open-weights model, hosted on a Compute Engine GPU VM or on Cloud Run in your own Google Cloud project. An open-source server exposes the same API in front of it, so the routing code in this article only needs a different endpoint. Our results come from Jev, so measure accuracy and latency on your own tasks before switching, and keep in mind that a self-hosted model is billed by the GPU-hour rather than by the token.

Taken together, the results give three practical rules.

Start with Flash on low thinking before you build a router. It solved all 50 tasks and cost considerably less than the default setting. Lowering the output token limit is not a substitute, because it doesn't reduce how much the model thinks on easy tasks. Set the thinking level directly, with thinkingLevel: "LOW".

Use Jev to route short, standalone tasks. Send simple tasks to Flash-Lite and hard ones to Flash on low thinking. Ask Jev one simple yes-or-no question per factor. In our test, this helped reduce cost and response time compared with running Flash on low thinking for everything, and came close to what a perfect router would achieve. Keep long, context-heavy turns on a single model so caching keeps working. For high-volume warehouse workloads, Jeff Nelson's BigQuery and Cloud Run cascade pattern applies the same idea.

Measure what your agent actually spends. Send your agent's traces and thinking-token counts to Cloud Logging and BigQuery, so you can see which tasks drive your spend and catch truncation or retries that inflate it. The benchmark code will be published after open-source review.

In summary, the most cost-effective way to run an agent is to match each task to the model that fits it. Start with a fast model on a light setting. You'll often find it already gets the job done. Then add a small, almost free classifier like Jev to send only the hard tasks to a stronger model, and ask simple yes-or-no questions rather than one broad one. Judge every option by what it costs per task done right, not per token.
