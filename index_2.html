Most accessibility problems on a website aren't hard to fix. Low-contrast text. An image with no alt text. A button that doesn't tell a screen reader what it does. None of these need a rebuild or a specialist.

Every year, WebAIM scans the home pages of the top million websites and checks them against basic accessibility standards. The 2026 report found that almost 96% of the pages scanned had at least one automatically detectable accessibility failure.

What stands out even more is what the errors actually are. The same problems have topped this report for seven years in a row. These aren't new, complex edge cases; they are the same simple, repeating mistakes.

In this guide, we'll look at what those top errors actually are, why they keep making it to production, and the simple workflow habits you can use to catch them before your users do. We'll also cover where tools like TestMu AI's Accessibility Testing Suite fit into that workflow.

It's easy to assume teams just don't care. But that's rarely the reason. Most developers know what alt text is for. Most designers know low contrast is a problem. The real issue is simpler; a few patterns explain most of it:

None of these come from not knowing accessibility rules. They come from how software is actually built: fast, in multiple moving pieces, with much of the page assembled from components and third-party code that nobody on the team wrote from scratch.

WebAIM's report found that a small number of accessibility issues account for most detectable WCAG failures across the top one million websites. The sections below explain what each issue is, why it matters, and how to fix it.

This is the single most common accessibility error, appearing on nearly 84% of homepages, according to WebAIM.

Poor contrast means the text color is too close to the background color, making it hard to read. For instance, light gray text (#999) on a white background (#FFF) yields a contrast ratio of 2.85:1, which is well below the standard requirement. For anyone with low vision or color blindness, that text becomes unreadable.

The Fix: WCAG asks for a contrast ratio of at least 4.5:1 for normal text. Running a quick check with tools like the WebAIM Contrast Checker or a Lighthouse audit will give you the exact ratio before your page ships. Because the tools lay it out so clearly, this is easily one of the quickest errors on this list to catch and fix.

Alt text is the written description a screen reader reads out loud in place of an image. Without it, a screen reader either skips the image entirely or announces the file name, which tells a user nothing about the image.

For example, if it's a product photo, a chart, or an icon that functions as a button, missing alt text means a screen reader user has no idea what they're looking at, what it does, or what happens when they click it.

The Fix: Describe what the image actually shows instead of just saying it's an image. If it's purely decorative and adds nothing a screen reader user needs, use an empty alt attribute (alt="") instead of leaving it off. That tells the screen reader to skip it cleanly.

Missing form labels appeared on 51% of home pages. This one is easy to miss because the form inputs often still look labeled. A form field looks perfectly labeled on screen when the label is simply placed next to the input box. A sighted user sees "Email" written next to a box and knows what to enter.

A screen reader, however, doesn't rely on visual placement. It relies on the HTML. If "Email" isn't actually connected to that input field in the markup, the field may be announced as simply "edit text" or "blank," leaving the screen reader user with no indication of what information it expects.

Placeholder text isn't a substitute either because it disappears as soon as the user starts typing.

Nearly half of all homepages contain links with no accessible name. The most common examples are icon-only links, such as a search icon, shopping cart, or social media icon. Sighted users recognize these icons immediately, but a screen reader may announce them simply as "link," giving users no indication of what each one does.

The Fix: Give every icon-only link an accessible name using visible text, aria-label, or another appropriate labeling method. This preserves the visual design while allowing screen readers to announce the link's purpose.

About 31% of home pages have buttons with no accessible name, and the share has risen every year since 2021. The usual culprits are icon-only buttons: a hamburger menu, a close "X" on a modal, a play button, or a carousel arrow. A screen reader announces these as just buttons, so users can't tell whether they open a menu, close a dialog, or submit a form.

The Fix: Give every button an accessible name. Use visible text where you can. For icon-only buttons, add aria-label (for example, aria-label="Close dialog") or visually hidden text inside the button. If the icon is an image, provide alt text that describes the action, not the image.

Around 14% of homepages don't specify the page's language. Without it, screen readers have to guess how the text should be pronounced, which can result in words being read with the wrong pronunciation or accent.

Many users rely on a keyboard instead of a mouse to navigate a website. If a menu only opens on hover, a custom dropdown only responds to clicks, or a button can't receive keyboard focus, those controls become unusable for them.

The Fix: Every interactive element should be reachable with Tab and Shift+Tab and operable with the keys users expect: Enter for links and buttons, Space for buttons and checkboxes, arrow keys inside menus, tabs, and radio groups, and Escape to close dialogs and menus. You can test this by trying to navigate the entire page using only the keyboard.

Developers sometimes remove the browser's default focus outline to improve the visual design but don't replace it with another focus style. As a result, keyboard users can no longer tell which element is currently selected as they move through the page.

The Fix: Never remove a focus outline without providing a clear replacement. Every interactive element should have a visible, high-contrast focus indicator that tells keyboard users where they currently are on the page.

Videos without captions exclude people who are deaf or hard of hearing and make content harder to follow when audio isn't available or practical. Captions also help users understand speech in noisy environments or when the audio quality is poor.

The Fix: Provide accurate captions for every video. If the video contains important spoken information, include a transcript as well. Automatically generated captions are a good starting point, but they should always be reviewed for accuracy.

On mobile, small buttons and links are hard to hit accurately. Users may tap the wrong control, trigger an unintended action, or have to try multiple times before the touch registers. WCAG 2.2 Level AA sets a minimum target size of 24x24 CSS pixels, with 44x44 CSS pixels recommended (WCAG AAA and Apple's own guidance).

The Fix: Give every tappable element enough size and padding to be reliably tappable, even if the visible icon inside it remains small. Aim for 44x44 CSS pixels, and never go below 24x24.

Run a scanner across a page, and it catches a good chunk of what's wrong. Missing alt attributes, contrast ratios below the required threshold, a form field with no label in the code. Automated scanners catch these immediately.

According to most industry estimates, automated tools catch about 30 to 40 percent of accessibility issues. That's worth running. It also means most of what actually breaks a page isn't something a scanner can see at all.

Take alt text, for instance. A scanner can confirm an image has an alt attribute. It can't tell you if that attribute says anything useful. "Image description here" and an actual description of the photo both pass the same check because the tool only confirms the field isn't empty.

Take another example of a custom div button with role="button". A scanner sees the role and perceives it as a button. It has no way of knowing that nobody added the keyboard handling that makes the button actually work, because that's not something a static scan can test. You'd only catch it by unplugging your mouse and tabbing through the page yourself.

Reading order works the same way. A page can pass every automated check and still present its content in an order that makes no sense once you strip away the layout and just listen to it, top to bottom.

None of this means automated tools aren't worth using. It means they're a baseline, not a final check. Treating a clean scan as proof that a page works is exactly how these errors keep making it to production in the first place.

Most of the errors covered here aren't difficult to fix on their own. The harder part is catching them before they enter your codebase. The best time to find these problems is while you're designing, building, and reviewing a feature, not right before a release.

Automated testing should be part of that process. It catches common issues quickly, right as they're introduced, but it isn't a substitute for manual testing. A clean scan only tells you that no automatically detectable issues were found.

That's what accessibility actually comes down to. It is not just a standard to meet, but the same usability you already care about, extended to people who navigate a page using assistive technologies.

This article walks through two working hooks — a pre-write gate and a post-edit lint pipeline — that enforce conventions deterministically.

Claude Code hooks solve a problem that every developer running agentic coding sessions eventually hits: the AI drifts from project conventions, and soft instructions in the prompt cannot prevent it. A popular r/Frontend post captured this precisely. The developer reported that Claude Code wrote roughly 1,000 lines of code for a simple helper function that already existed in a project dependency. The prompt stated the project conventions. Claude ignored them anyway. The result was duplicated logic, bloated output, and wasted review time.

The root cause is structural, not incidental. Prompt-based instructions are probabilistic. They work well in short sessions, but as the context window fills during extended agentic loops, earlier instructions degrade in influence. Tool outputs, file contents, and intermediate reasoning bury the initial convention reminders. A long enough session means the agent effectively forgets what it was told. Any enforcement mechanism that relies solely on prompt text will exhibit this degradation pattern.

Claude Code hooks offer an alternative enforcement mechanism: shell scripts that bind to lifecycle events inside the agent loop. These scripts use exit codes to enforce rules. Exit 0 means proceed. Exit 2 blocks the action, and the script's stderr is surfaced to Claude as feedback. Any other non-zero exit code is a non-blocking error. This is deterministic. No matter how full the context window gets, an exit code of 2 stops the action every time.

By the end of this article, you will have two working hooks: a pre-write gate that forces Claude to verify whether an implementation already exists before writing new code, and a post-edit lint and format pipeline that runs Prettier and ESLint on every changed file. Together, these hooks catch duplicated or unnecessary code before it lands and enforce style rules automatically.

Prerequisites: Claude Code installed and functional; a Node.js project with Prettier and ESLint already configured; jq installed (brew install jq / apt install jq); Prettier and ESLint must be installed as local node_modules dependencies (not relied upon via npx remote fetch); and basic familiarity with Bash scripting.

Hooks operate on an event-driven model. They fire at specific points in Claude Code's agent loop, intercepting actions before or after they occur. Four lifecycle events are relevant:

PreToolUse fires before any tool call executes. This is the interception point for blocking actions. For file-write gating, the tool names to match are Write, Edit, and MultiEdit. You can also match against Bash for command-level gating.

After a tool call completes, PostToolUse runs. This is the point for validation: linters, formatters, or test suites check the result of an edit. Because the tool has already executed, an exit code of 2 from a PostToolUse hook does not block the original action. Instead, it surfaces the script's stderr as feedback to Claude, which can then issue a follow-up edit to correct the issues.

When the user submits a new prompt, UserPromptSubmit fires. This is useful for resetting state between conversational turns.

Notification fires when Claude sends a notification. Non-zero exit codes from Notification hooks do not block any action. (The documentation does not specify any exit-code effect for this event type.) This makes it useful only for logging or side effects.

The contract is simple. When a hook script exits with code 0, the action proceeds normally. Exit code 2 is the blocking signal. For PreToolUse, exit 2 blocks the tool call and the script's stderr is fed to Claude as feedback. For PostToolUse, the tool has already completed, but exit 2 surfaces the script's stderr to Claude, which can take corrective action. #11174. React useEffect Cleanup Patterns for Timers, Listeners, and Fetch Races

Missed cleanup functions in React useEffect are among the most common sources of memory leaks, stale-state bugs, and race conditions. Typical beginner tutorials demonstrate the happy path: fetch data, set state, render. They rarely address what happens when a component unmounts mid-flight, when a dependency changes faster than an async operation resolves, or when event listeners silently pile up across re-renders. This article provides a unified mental model for useEffect cleanup across three categories (timers, listeners, and fetch races), a reference table mapping setup to cleanup to pitfall, and a copy-paste PR review checklist that development teams can adopt immediately.

The mental model is simple: React runs the setup function when the component mounts, runs the cleanup function when the component unmounts, and on every dependency change, runs cleanup for the previous render's effect before running setup for the current render's effect. This cleanup-then-setup cycle on dependency change is the part most developers either overlook or misunderstand. It means that every effect invocation is paired with a corresponding teardown, and React guarantees that ordering. The setup function acquires resources; the cleanup return releases them. The dependency array declares which values, when changed, trigger that cycle again.

React 18's StrictMode intentionally runs each component's effect twice in development by simulating an unmount and remount: setup → cleanup → setup. Your setup function executes twice on the initial render in development. This double invocation exists specifically to surface missing cleanup logic. If a component registers an event listener in setup but never removes it in cleanup, StrictMode will produce two listeners after the simulated remount, making the bug immediately visible during development. As documented in the React docs on StrictMode (https://react.dev/reference/react/StrictMode), this behavior only occurs in development mode and does not affect production builds. However, the bugs it exposes are entirely real. A component that behaves incorrectly under StrictMode's double-mount has a latent cleanup bug that will manifest in production whenever the component remounts due to navigation, conditional rendering, or parent re-renders.

When a setInterval starts inside a useEffect that depends on a prop or state value, every time that dependency changes, React re-runs the effect. Without cleanup, the previous interval continues running. A second interval starts. Then a third. The observable symptom depends on what the interval does: a counter increments N times per tick (where N is the number of orphaned intervals), a polling callback fires multiple times per tick, or a UI animation speeds up erratically. Each orphaned interval holds a closure over stale state, compounding the problem. Under StrictMode's double-mount in development, this bug surfaces immediately as two intervals running from the very first render.

The correct pattern creates the interval in setup and clears it in cleanup. When the dependency changes, React clears the old interval before starting a new one with the updated value. This guarantees exactly one active interval at any point in time.

The same principle applies to setTimeout. Replace setInterval with setTimeout and clearInterval with clearTimeout. Store the timer ID returned by the scheduling function, then clear it in the cleanup return.

Adding an event listener to window, document, or any DOM node outside the component's own render tree requires manual cleanup. Without a matching removeEventListener in the cleanup return, every re-render (or StrictMode double-mount) attaches an additional handler. The handlers accumulate. A resize listener that updates state will trigger setState multiple times per resize event, once for each orphaned listener. This degrades performance and can cause subtle state corruption when multiple handlers race to update the same state variable.

The critical detail is that removeEventListener must receive the exact same function reference passed to addEventListener. An inline arrow function created inside the effect body produces a new reference on every invocation, so calling removeEventListener with a different inline arrow does nothing. The listener is never removed. Declare the handler as a named function (or a variable holding the function) inside the effect, then pass that same variable to both addEventListener and removeEventListener.

If the handler depends on a prop or state value and is defined outside the effect (for example, with useCallback), that handler must appear in the dependency array. When the reference changes, React cleans up the old listener and attaches the new one. Note that re-adding the listener on each dependency change is correct behavior: the old handler (with stale closure) is removed and the new handler (with fresh values) is attached.

Consider a search component where the user types quickly. Each keystroke triggers a new fetch. The request for "rea" might take 300ms while the request for "react" takes 50ms. The "react" response arrives first, and the UI shows the correct results. Then the "rea" response arrives, and because nothing prevented it from calling setState, it overwrites the UI with stale, incorrect results. This is a classic race condition. The slower response wins not because it is more recent, but because it resolves later. Without cancellation, there is no mechanism to tell the browser to discard an in-flight request whose results are no longer relevant.

The modern solution is AbortController. Each effect invocation creates a new controller instance. The controller's signal property is passed to fetch as an option. When the cleanup function runs (because the dependency changed or the component unmounted), it calls controller.abort(), which cancels the in-flight request. The fetch promise rejects with an AbortError. Browsers generally attempt to cancel the underlying network request as well, though the behavior varies by engine (see the Fetch spec on AbortSignal and MDN's browser compatibility tables). This guarantees that only the most recent request can successfully set state.

Calling abort() rejects the promise. This is normal, not an error condition. The catch block must distinguish AbortError from genuine network failures. Without this guard, the UI would flash an error for every intentional cancellation, or the rejection would trigger error-logging infrastructure. The standard check inspects the error's name property: if it equals 'AbortError', the catch block returns early without updating state or surfacing an error.

Note that the effect function itself is not async. An inner async function is declared and called immediately. This matters because useEffect expects its return value to be either undefined or a cleanup function. React ignores a returned promise and never registers a cleanup function from it.

Website performance is an essential part of modern web development. A visually attractive website may still frustrate users if its pages load slowly, interactions feel delayed, or content shifts unexpectedly during loading. These problems can affect usability, accessibility, and business outcomes.

Improving performance does not always require a complete redesign or a complicated optimization framework. Many improvements come from understanding how browsers load resources, reducing unnecessary work, optimizing images, and delivering only the code a page actually needs.

The first step in performance optimization is understanding how a website behaves under real conditions.

Forms are among the most important components of modern websites. They allow users to register accounts, submit contact requests, search for information, complete purchases, and interact with web applications.

A single transient database or CMS outage during Next.js ISR background revalidation can silently replace a perfectly valid cached page with a persistent 404. This is not a theoretical risk. Developers using Next.js ISR with notFound() have reported this exact failure mode, where a temporary infrastructure hiccup causes SEO damage and user-facing downtime that persists long after the underlying service recovers. The root cause is a common error-handling pattern that conflates "the data source is unreachable" with "this record does not exist." This article presents a concrete architectural fix that separates those two states, prevents Next.js from ever caching an error-driven 404, and provides an on-demand revalidation recovery strategy.

In the Next.js App Router, Incremental Static Regeneration operates on a stale-while-revalidate lifecycle. When you set a revalidate interval on a page, the first request generates and caches it. Subsequent requests within that window serve the cached version. Once the interval expires, the next request still receives the stale page, but Next.js triggers a background revalidation. This background render re-executes the page's data-fetching logic and, if successful, replaces the cached output with the fresh render.

The critical detail: the background revalidation replaces whatever is in the cache. If that render produces a 404 response, Next.js caches the 404 and overwrites the previously valid page.

The scenario, reported on Stack Overflow, follows a pattern that exists in countless Next.js codebases. A data-fetching helper wraps a CMS or database call in a try-catch block that returns null on any error, whether that error is a network timeout, a 500 from the upstream API, or a genuine "record not found" response. The page component then checks for null and calls notFound().

During a transient outage, the ISR background render hits the data-fetching error path, receives null, triggers notFound(), and the resulting 404 response is cached. The previously valid, fully rendered page is gone. When the infrastructure recovers seconds or minutes later, the damage is already done. The 404 persists until the next revalidation cycle, and if the timing is unlucky, users and search engine crawlers see a 404 for up to one full revalidation interval (60 seconds in this example, but potentially hours in production configs).

AI coding tools can turn a plain-English description into a working web application in minutes. They can generate interfaces, connect APIs, create database schemas, and help developers move from an idea to a functional prototype faster than traditional workflows often allow.

AI can accelerate implementation, but production readiness still requires engineering discipline.

Whether you are a developer using an AI coding assistant, a founder building a minimum viable product (MVP), or a team experimenting with vibe coding, this checklist will help you evaluate your application before releasing it to real users.

Vibe coding is an AI-assisted software development approach in which developers describe requirements in natural language and use AI tools to generate, modify, and debug code. Rather than manually writing every component, developers guide implementation through prompts, feedback, and iterative refinement.

This approach can accelerate prototyping, interface development, and repetitive programming tasks. However, generated code must still meet the same quality standards as conventionally written software.

Consider a customer portal. An AI tool might generate a login page, a dashboard, and a database connection in a single session. The interface could look complete while the application still lacks proper authorization checks, reliable error handling, or protection against unauthorized data access.

These gaps become more consequential when an application stores personal information, processes payments, manages business records, or serves multiple customers.

Production readiness means an application has been tested and configured to operate reliably in its intended environment. It includes security, correctness, performance, maintainability, monitoring, and recovery.

Before deployment, evaluate the application across the following areas.

One common mistake in AI-assisted development is building features before defining what they should do.

A prompt such as "Build a project management dashboard" leaves important questions unanswered. Who can create projects? Can users access another person's tasks? What happens when a task is deleted? Which fields are mandatory? How should errors appear?

When these decisions are left to the AI, the implementation may reflect assumptions that do not match the product's requirements.

Before generating substantial amounts of code, document:

Core functionality: What must users be able to accomplish?

User roles: Who can view, create, edit, or delete information?

Data requirements: Which fields, relationships, and constraints are necessary?

Technical constraints: Which frameworks, databases, APIs, and hosting environments will be used?

Failure scenarios: What should happen when a request fails or data is invalid?

Acceptance criteria: What observable result proves that each feature works correctly?

For example, a task management application might have this requirement:

A user can view and modify only the tasks belonging to projects they are authorized to access. Unauthorized requests must be rejected without revealing protected data.

This is more useful than simply asking an AI tool to "add secure task management." It establishes a behavior that developers can implement and test.

Once the requirements are documented, ask the AI to implement one coherent feature at a time. Review the output before moving to the next feature.

This makes unexpected changes easier to identify and reduces the risk of introducing multiple interacting bugs through a single large generation.

Keep the requirements in a project document and update them whenever product decisions change. The specification should remain the reference point for both the developer and the AI coding assistant.

A functional interface can conceal serious implementation problems.

AI-generated code may contain duplicated logic, unnecessary dependencies, outdated API usage, incorrect assumptions about framework behavior, or abstractions that make future changes difficult. A successful build does not establish that the application behaves correctly.

Code review is therefore essential, even when an AI tool generates most of the implementation.

Start with the code responsible for important application behavior:

Check whether functions have clear responsibilities, whether data flows are understandable, and whether dependencies are actually needed.

For JavaScript and TypeScript projects, automated linting and type checking can catch many common mistakes. However, these tools cannot prove that business logic is correct or that permissions are enforced properly.

When reviewing a change, ask the AI to explain its implementation and identify its assumptions. Then verify those explanations against the actual code and relevant documentation.

If a function is difficult to understand, simplify it or request a clearer implementation. Code that nobody on the team can confidently maintain is a liability, regardless of how quickly it was generated.

Authentication answers the question, "Who is this user?" Authorization answers, "What is this user allowed to do?"

Both are necessary for applications that protect private information or restrict access to particular features.

An AI-generated application may implement a login screen and assume the security requirement is complete. In reality, hiding a dashboard element or redirecting an unauthenticated visitor does not prevent someone from calling a protected API directly.

Testing is particularly important in vibe coding because generated code can appear convincing even when it implements the wrong behavior.
